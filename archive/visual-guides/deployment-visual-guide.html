部署推理：从模型到机器人动作

训练完成只是开始——让模型在真实机器人上可靠运行才是真正的挑战。

你花了一周训练了一个 VLA 模型，在离线数据集上 loss 很低、评测指标也不错。然后你把 checkpoint 加载上去，让机器人跑了一下——它犹豫了 2 秒才输出第一个动作，然后突然猛冲、撞翻了杯子。

为什么？因为部署推理不是 "model.predict(obs)" 这一行代码。它是一条从传感器到电机的完整链路，每一环都有可能出错。这一页带你走一遍这条链路。

2. 预处理一致性：最常见的 bug 来源

模型训练时做了什么预处理，部署时就必须做完全相同的预处理。差一步就会导致性能断崖式下降。

训练时（保存这些）

image_size: [224, 224]
crop: center_crop
normalize:
  mean: [0.485, 0.456, 0.406]
  std:  [0.229, 0.224, 0.225]
action_norm:
  type: min_max
  min: [-0.05, -0.05, ...]
  max: [+0.05, +0.05, ...]
state_norm:
  mean: [0.12, -0.45, ...]
  std:  [0.08, 0.12, ...]

部署时（必须加载并使用）

config = load("preprocess_config.yaml")

img = resize(img, config.image_size)
img = center_crop(img)
img = (img - config.normalize.mean)
       / config.normalize.std

action_raw = model.predict(img, state)
action = denormalize(
    action_raw,
    config.action_norm
)
反归一化的陷阱

训练时归一化方法有两种：

  • z-score：action = (raw - mean) / std → 还原：raw = action × std + mean
  • min-max：action = (raw - min) / (max - min) → 还原：raw = action × (max - min) + min

如果训练用了 z-score 但部署时用 min-max 反归一化——动作幅度会完全错误。归一化配置必须随 checkpoint 一起保存和加载。

3. Action Chunk 和 Receding Horizon

如果模型每次推理需要 200ms，但机器人需要 10Hz（每 100ms 一个动作），怎么办？

答案就是 Action Chunk（动作块）。模型一次输出未来 H 步的动作，机器人先执行着；等下一次推理结果出来了，用新的预测替换剩余的旧动作。这就是 Receding Horizon（滚动视界）。

Receding Horizon：模型推理和动作执行交替进行，chunk 填补推理延迟

chunk_size 怎么选？

chunk 太短（如 H=2）→ 模型来不及推理就用完了，机器人会"卡顿"。
chunk 太长（如 H=64）→ 预测太远的未来不准确，前半段还在执行旧预测时世界已经变了。
经验值：H = 4 ~ 16，根据推理延迟和控制频率调节。ACT 论文默认 H=100（50Hz×2s），π₀ 常用 H=16。

4. 推理服务：本地还是远程？

模型在哪里跑？根据场景不同，有三种常见部署方式：

本地推理

模型跑在机器人本体或连接的工控机上。延迟最低，但受限于机载算力。

适合：小模型（<1B 参数）、实时控制、不能联网的场景

远程推理

图像通过网络发给 GPU 服务器，服务器返回动作。算力充足，但网络延迟是瓶颈。

适合：大模型（7B+）、研究实验、有低延迟内网的环境

对比本地推理远程推理
延迟模型推理时间（50-300ms）模型 + 网络往返（100-500ms）
可靠性不依赖网络网络断了机器人就停了
算力受限于机载 GPU（如 Jetson）可以用 A100 / H100
模型大小通常 < 1B可以跑 7B-70B
典型方案TorchScript / ONNX / TensorRTHTTP / gRPC 服务 + 客户端
实际中常见的混合方案
远程 GPU 跑 VLA 大模型（比如 OpenVLA 7B），输出一个 action chunk。本地小 MCU 负责安全检查和高频控制（1kHz 伺服）。action chunk 通过 WiFi/以太网传输，本地按 chunk 逐步执行，不需要每步都等远程。

5. 安全检查：机器人的"刹车系统"

模型可能输出任何东西——包括让机器人撞桌子或超速运动的动作。安全检查是部署中最不可省略的一环。

安全检查是串联的——每一关都必须通过

安全检查绝对不能跳过

即使是经过充分训练的模型，在遇到训练分布外的情况时也可能输出"疯狂"的动作。安全检查不是调试工具——它是生产必需品。每次执行都必须检查，不能因为"模型在测试中表现很好"就跳过。

  • Watchdog：如果推理超时未响应，自动停止机器人
  • 人工接管：随时可以按下急停按钮，切到手动模式
  • 力矩监控：如果电机力矩突然飙升，说明可能在碰撞

6. 日志和可追溯性

机器人抓空了——是模型预测错了，还是感知出了问题，还是安全检查误杀了正确动作？要回答这个问题，需要完整的执行日志。

每次推理应该记录：

记录项内容用途
model_versioncheckpoint 路径 + commit hash确认跑的是哪个版本
observation原始图像路径、关节状态、timestamp复现输入条件
raw_action模型直接输出（归一化值 / token）区分是模型还是后处理问题
processed_action反归一化后的真实动作确认反归一化是否正确
safety_check每项检查的通过/失败 + 原因确认是否被安全检查截断
sent_action最终发给控制器的命令确认控制器收到了什么
latency_ms每个环节的耗时发现性能瓶颈
排错黄金法则
如果机器人行为异常，按这个顺序检查：
1) 图像是否正常（曝光、分辨率、是否黑屏）？
2) 预处理是否和训练一致（resize、normalize、crop）？
3) 模型输出是否合理（raw_action 范围是否正常）？
4) 反归一化是否正确（processed_action 量级对不对）？
5) 安全检查是否误杀（safety_check 日志）？
6) 控制器是否正确执行（sent_action vs 实际关节状态）？
90% 的部署 bug 出在步骤 2 和 4。

7. 部署上线清单

在让模型控制真实机器人之前，检查这张表：

#检查项验证方法
1Checkpoint 和 norm stats 配套加载 checkpoint 和对应的 yaml，确认时间戳匹配
2图像预处理完全一致离线对比：训练 dataloader 和部署 preprocessor 输出相同
3动作空间正确检查 action 维度、类型（joint/EE/delta）、单位、坐标系
4反归一化正确用训练数据做一次 normalize → denormalize，确认恢复原值
5安全限位已设置手动发一个极端动作（如全零或全最大值），确认被截断
6Watchdog 工作故意断开模型服务，确认机器人在超时后停止
7急停按钮可用运行中按急停，确认机器人立即停止
8日志在记录跑一次推理，检查日志文件包含所有必要字段
9离线 → 在线一致性用训练集中的一条轨迹做 rollout，确认动作序列接近原始
10低速先跑先用 50% 速度运行，观察几次后再提到全速
一句话总结
部署推理 = 预处理一致性 + 反归一化正确 + action chunk 填延迟 + 安全检查全覆盖 + 完整日志。这五样缺一个，都不能说"部署完成"。
