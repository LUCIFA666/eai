# 训练视频模型与动作策略

目标：把论文中的两阶段方法和仓库中的训练、评测入口对应起来，并给出一个适合初学者的复现顺序：先评测主链路，再回头理解训练。

读完这一页，应当能够回答两个问题：

1. 论文中的第一阶段、第二阶段，在代码里分别由哪些入口承担。
2. 如果要复现论文，为什么第一次通常应先跑闭环评测，再讨论完整训练。

对初学者来说，这一章最容易混淆的是三件事：

1. 第一阶段视频模型训练
2. 第二阶段动作策略训练
3. 第二阶段动作策略评测

如果不先把这三件事拆开，就容易在阅读脚本时失去主线。

## 先把三类入口对应起来

| 任务 | 典型入口 |
|---|---|
| 第一阶段视频训练 | `step1_train_svd.py` |
| 第二阶段动作训练 | `step2_train_action_calvin.py` / `step2_train_action_xbot.py` |
| 第二阶段闭环评测 | `policy_evaluation/calvin_evaluate.py` |

这三类脚本关注的问题完全不同：

- 第一阶段训练：视频模型是否学到了机器人未来动态
- 第二阶段训练：动作头是否学会使用未来表征
- 第二阶段评测：策略在环境中能否连续完成任务

## 先用一句话概括论文复现顺序

如果把论文复现分成“看懂”和“跑通”两个层次，一个更稳的顺序通常是：

1. 先看懂第一阶段和第二阶段分别做什么
2. 先跑通第一阶段推理
3. 再跑通第二阶段闭环评测
4. 最后才进入完整训练和数据迁移

这也是这一章的组织逻辑。

## 为什么第一次复现时应先看评测

如果目标是“先确认项目是否真的能工作”，那么最值得优先打通的不是完整训练，而是第二阶段的闭环评测。这是因为：

- 训练耗时更长
- 依赖更多自定义数据
- 一旦出现问题，定位范围会更大

相比之下，闭环评测更适合回答一个直接问题：

**在现成模型和现成数据上，这套系统能不能真正完成动作控制。**

## 第一阶段训练在做什么

第一阶段的底座通常是 Stable Video Diffusion。训练目标不是单纯让视频“更好看”，而是让它更适合表达机器人操控中的未来动态，例如：

- 机械臂接近目标时的运动趋势
- 接触发生后的场景变化
- 不同语言指令对应的未来演化差异

对第二阶段来说，更重要的不是最终生成视频本身，而是视频模型内部形成的中间时空特征。

因此，第一阶段是否成功，不能只看 loss，还要回到 `make_prediction.py` 的视频结果本身。如果预测视频已经明显偏离任务语义，那么第二阶段很难仅靠动作头把问题完全补回来。

## 第二阶段训练在做什么

第二阶段的核心不是“重新训练一个普通视觉策略”，而是：

1. 调用第一阶段视频模型
2. 从中间层提取特征
3. 用 `Video Former` 等模块做进一步聚合
4. 用条件动作扩散头输出未来若干步动作

因此，第二阶段训练真正关注的是：

- 哪一层视频特征更适合作为动作条件
- 这些特征如何压缩成策略可用的 token
- 动作扩散头能否稳定地输出 action chunk

这也是为什么阅读 `VPP_policy.py` 和 `diffusion_extract.py` 非常关键：它们直接决定“未来表征”在代码中到底如何进入动作策略。

## CALVIN 评测在做什么

`policy_evaluation/calvin_evaluate.py` 测试的不是视频生成质量，而是完整闭环：

1. 当前观测进入策略
2. 策略提取视频模型中间特征
3. 输出动作
4. 环境执行 `step(action)`
5. 统计任务是否成功

这一点和第一阶段 `make_prediction.py` 的作用完全不同。前者关注“策略能不能完成任务”，后者关注“视频模型如何理解未来”。

## 论文复现里，评测为什么是关键节点

从论文视角看，第二阶段评测承担的是“最终方法是否成立”的验证角色。因为只有评测真正回答：

- 视频模型内部特征是否真的帮助了动作策略
- 这套两阶段架构是否能够在环境中连续完成任务

因此，对初学者来说，`calvin_evaluate.py` 不是一个附属脚本，而是整条论文主线的闭环验证入口。

## 一个较适合初学者的最小评测命令

如果希望先验证闭环链路，较常见的做法是先用 debug 数据集，并把序列数设小：

```bash
python policy_evaluation/calvin_evaluate.py \
  --video_model_path /path/to/models/vpp/svd-robot-calvin \
  --action_model_folder /path/to/models/vpp/dp-calvin \
  --clip_model_path /path/to/models/vpp/clip-vit-base-patch32 \
  --calvin_abc_dir /path/to/datasets/calvin/calvin_debug_dataset
```

这里的目的不是立刻复现论文最终数值，而是先确认：

- 模型可以加载
- CALVIN 环境可以启动
- 闭环评测可以完成
- 结果可以正常保存

需要注意的是，上面的命令对应原仓库的参数形式。原仓库命令行默认并不会暴露所有评测规模和日志控制开关；如果需要更细的控制，通常需要修改配置文件或脚本。

## 如何读一组基础评测结果

以一组 `50` 条 debug 序列的示例结果为例：

```text
Average successful sequence length: 4.4
1/5: 96.0%
2/5: 94.0%
3/5: 92.0%
4/5: 80.0%
5/5: 78.0%
```

这组结果可以解释为：

- 平均每条 long-horizon 序列能连续完成 `4.4 / 5` 个子任务
- 至少完成 1 个子任务的比例是 `96%`
- 至少完成 5 个子任务的比例是 `78%`

对最小复现来说，这类结果已经足以说明：

- 第二阶段主链路不只是“可以启动”
- 它已经能够在 debug 数据上给出稳定的闭环表现

## 为什么还要看任务级别的细项

平均指标只是第一层信息。更细的 `task_info` 往往还能暴露出：

- 哪些子任务已经接近 `100%`
- 哪些动作类型明显更弱

例如，在一组示例结果里，常见的现象可能是：

- 开关抽屉、移动滑门、抓取等任务表现较稳定
- 某些方向性的 pushing 任务更容易失败

这种信息很重要，因为它提示问题可能不是“模型整体没学会”，而是某一类局部动作仍然存在偏置。

## 评测可视化为什么值得看

在 `calvin_evaluate.py` 的运行过程中，脚本可能会保存部分 rollout 视频。它们的价值不是展示“好看的视频”，而是帮助判断：

- 策略是否在持续接近正确目标
- 子任务切换时是否稳定
- 失败是卡在接近、抓取还是放置阶段

## 实际复现中常见的工程问题

第一次跑评测时，最常见的故障通常不是算法问题，而是工程细节问题，例如：

- `numpy` 与 `torchvision` 的 ABI 冲突
- `pkg_resources` 缺失
- `pyhash` 依赖安装失败
- debug 数据旧下载地址失效
- `last.pt` 目录结构或命名方式不符合脚本假设
- `wandb.log()` 早于 `wandb.init()`

这些问题集中说明了一点：原始项目更接近研究代码，而不是面向初学者打磨好的公共工具。因此，第一次复现时建议先使用小规模评测，再逐步扩大规模。

## 如果之后要进入完整训练，应先记住什么

在主链路已通之后，再回头看训练会更容易：

- 第一阶段训练看视频预测质量
- 第二阶段训练看动作头如何消费视频特征
- 评测阶段再看闭环任务结果

这样一来，三类问题的边界会更清楚，不容易把所有问题都混成“模型效果不好”。
