# 延迟预算与评测术语

## 本节目标

本节界定后续延迟分析中反复用到的几个术语：单次推理的时间由哪几段构成、控制频率为单步推理预留多少延迟预算、单步延迟与动作块刷新频率如何共同决定 rollout，以及报告延迟时 mean / median / p95 / max 各自反映什么。

## 一次推理的时间组成

一次推理从读入观测到给出动作，时间花在几个串联的阶段上，加速方法各自针对其中一段：

- 视觉编码：把图像切成 token，经视觉 backbone 做一次前向。这一段随输入分辨率和图像路数变化，分辨率越高、相机越多，token 越多，编码越重。
- LLM/VLM 前向：主干 Transformer 在视觉 token 和文本 token 上做注意力与前馈计算。它的开销跟参数量和上下文长度直接挂钩，多数 VLA 里这一段是单步延迟的主体。
- 动作生成：把主干输出变成具体动作，开销取决于动作的生成方式。自回归要一个 token 接一个 token 串行解码，token 越多越慢；flow 或 diffusion 要迭代采样很多轮，轮数越多越慢；并行动作头一次前向就生成一整段动作，这一段就大幅缩短。同样是 VLA，动作生成这一段的开销跨度很大，从几乎可忽略到接近主干前向的量级都有可能，差别完全在于范式。
- 反归一化与后处理：把归一化的动作还原成真实量纲，再做裁剪和平滑，计算量小，通常可忽略。
- 服务通信与运行时队列：policy server 的网络往返、观测与动作队列、控制频率匹配，属于运行时。

综合来看，可压缩的主要是三处：主干前向的规模、动作生成的范式、视觉 token 的数量。本章的三组加速技术正好分别落在这三处，后面每个方法都对应其中一段。

## 控制频率与时间预算

VLA 嵌在控制回路里：采集观测、推理出动作、执行、再进入下一轮。控制频率决定每一轮留给推理的时间。频率的倒数就是单步时间预算，50 Hz 对应大约 20 ms，10 Hz 对应大约 100 ms，常见的 10–50 Hz 控制频率，单步预算大致落在 20–100 ms。

预算给出了一个可判断的标准：一次推理的延迟落入这段窗口，回路就能按节拍持续运行；超出窗口，这一拍就没有新动作可用。超预算之后怎么办是运行时的调度策略问题，等待或重复上一个动作只是其中最简单的一种，还可以用历史动作外推、预取下一块动作缓冲、让推理循环与控制循环异步运行等方式吸收抖动，各自在动作平滑性和实现复杂度上取舍。但这些策略只能缓解偶发超标，无法替代把延迟本身降到预算以内。所以推理加速的目标不是一味追求速度，而是让单步延迟稳定地落入当前控制频率给的预算。

## action chunking、刷新频率与 rollout

如果每个控制步都要重新推理一次，单步预算会非常紧张，20 ms 内既要算完前向又要算完动作生成，多数 VLA 做不到。action chunking 放宽了这个约束：一次推理输出未来一小段连续动作，机器人依据这段动作连续执行若干控制步，执行期间不必重新推理。控制频率仍然由机器人按动作块逐步执行来维持，推理频率则降到"每隔若干步算一次"。

这样单步延迟就和控制频率解耦了，但引入了一个新的约束——动作块刷新频率，也就是下一块动作必须在多久内算出。机器人执行当前动作块要花一段时间，新一块必须在这段时间内推理完成。单次推理延迟一旦超过这个窗口，旧动作块执行完了，新块还没就绪，动作队列就会断流：机器人要么停顿，要么继续用过期动作，rollout 的成功率和动作平滑性都会随之下降。所以 chunking 之后，延迟预算从"每个控制步"放宽到了"每个动作块的刷新周期"，但延迟仍然要落入这个周期，否则同样会断流。动作块长度本身也不是越长越好：块越长，单块内不重新推理的步数越多，遇到意外扰动时最快也要等当前块执行完才能依据新观测重规划，这段等待就是反应延迟，会随块长增加。举例来说，控制频率 20 Hz、块长 8 时一整块约 400 ms，扰动即便立刻出现，也要等这 400 ms 才能响应。因此，块长是刷新频率和反应速度之间的取舍。动作块具体取多长、队列怎么衔接、要不要做时序聚合，属于运行时处理的问题。

## 延迟的统计口径

评估一个方法快多少，只看一个平均数不够，因为实时控制担心的是偶发的延迟尖峰，而不是平均延迟。常用四个统计量：

- mean：所有单步延迟的平均，反映总体水平，但被少数极慢值拉高后会掩盖分布形状。
- median（p50）：排序后的中位数，代表"典型一次推理"有多快，不受个别极值影响。
- p95：95% 的推理延迟都低于它，只有最慢的 5% 高于它，反映尾部延迟的严重程度。
- max：观测到的最慢一次。

实时控制更关注 p95 和 max，而不是 mean：哪怕平均延迟稳定落在预算内，只要尾部偶尔升高、超过刷新周期，这几次就会断流，在 rollout 上表现为偶发的卡顿或抓取失败。测延迟时还要把 warmup（预热）剔除——第一次推理常包含 CUDA 编译、kernel 自动调优、缓存预热，比稳定状态慢得多，纳入统计会让所有数字失真。这套口径也是后面比较各方法时报告延迟的统一标准。

## 小结

本节把"快"拆解为几个可以分别判断的方面：延迟落在视觉编码、主干前向、动作生成哪一段；单步或刷新周期的延迟有没有落入控制频率给的预算；刷新频率能否让动作队列不断流；以及读延迟时该看 mean 还是 p95、max。加速方法的收益和代价，都可以放进这套坐标对照来看。
