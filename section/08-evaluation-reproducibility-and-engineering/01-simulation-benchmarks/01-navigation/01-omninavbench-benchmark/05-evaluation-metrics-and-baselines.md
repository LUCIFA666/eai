# 1.5 评测指标

## 目标

OmniNavBench 的评测不是只看 agent 最后有没有到达终点，而是从任务完成度、路径效率、人类交互、问答表现和安全性等多个角度衡量导航能力。

本节主要介绍 OmniNavBench 中常用的评测指标，以及几类 baseline 方法在结果表格中应该如何理解。掌握这些指标后，阅读实验结果时就能更清楚地判断模型到底是完全失败、只完成了部分子任务，还是在某些能力上存在明显短板。

## 评测指标的整体结构

OmniNavBench 面向组合式导航任务，因此一个 episode 中通常包含多个子任务。评测指标需要同时回答几个问题：

```text
整条任务是否完成？
中间子任务完成了多少？
路径是否高效？
是否正确跟随人类目标？
是否保持合理社交距离？
是否能回答环境相关问题？
```

因此，它的指标可以分成几类：

| 指标类别 | 代表指标 | 主要关注点 |
| --- | --- | --- |
| 任务完成度 | SR、CSR、SGC、OSR | agent 是否完成任务，以及完成了多少中间目标 |
| 路径效率 | SPL | agent 是否用较短路径完成任务 |
| 人类交互 | HFS、HFR | agent 是否能稳定跟随目标人 |
| 问答表现 | EQA-ACC | agent 是否能基于环境观察回答问题 |
| 安全性 | SII | agent 是否过度接近人类并侵犯个人空间 |

论文中的指标表也采用了类似划分，其中 SR、CSR、SGC、OSR、SPL 用于衡量导航完成与效率，HFS、HFR 用于评估 human following，EQA-ACC 用于评估具身问答，SII 用于衡量 social intrusion，且 SII 是越低越好。

## SR：Success Rate

SR 是 Success Rate，表示完整 episode 的最终成功率。

在组合式导航中，SR 是一个比较严格的指标。只有当 agent 成功完成整条组合指令，并满足最终任务条件时，episode 才会被计为成功。

可以理解为：

```text
SR = 完整成功的 episode 数量 / 全部测试 episode 数量
```

例如，一个 episode 包含三个子任务：

```text
进入客厅
-> 找到垃圾桶
-> 返回起点
```

如果 agent 只完成前两个子任务，但没有成功返回起点，那么这个 episode 的 SR 仍然可能记为失败。

因此，SR 主要反映的是：

```text
agent 是否能够稳定完成完整长程任务
```

在组合式导航中，SR 往往比单任务导航中的成功率更低，因为任何一个阶段失败都可能导致整个 episode 失败。

## CSR：Completion Success Rate

CSR 是 Completion Success Rate，用来衡量 agent 严格完成了多少子指令。

与 SR 不同，CSR 不只看整条任务是否最终成功，而是关注组合任务中每个子任务的完成情况。

可以理解为：

```text
CSR = 已严格完成的子指令数量 / episode 中的子指令总数
```

例如，一个 episode 包含四个子任务：

```text
子任务 1：完成
子任务 2：完成
子任务 3：失败
子任务 4：未开始
```

那么这个 episode 的完整 SR 是失败，但 CSR 可以体现 agent 已经完成了前两个子任务。

CSR 的意义在于，它能区分两种不同情况：

```text
完全没有完成任何子任务
完成了部分子任务，但没有完成整条指令
```

对于组合式导航来说，这种区分非常重要。因为一个模型虽然最终失败，但如果能完成多个前置子任务，说明它仍然具备一定的阶段性能力。

## SGC：Sub-Goal Completion

SGC 是 Sub-Goal Completion，用来衡量 agent 在各个子目标上的连续完成进度。

CSR 更强调“是否严格完成”，而 SGC 更强调“接近完成到什么程度”。

例如，在 ObjectNav 中，agent 可能没有完全到达目标物体附近，但已经从很远的位置移动到了目标附近。此时严格完成率可能仍然是 0，但 SGC 可以反映它已经取得了一定进展。

可以简单理解为：

```text
CSR：
看子任务是否严格完成

SGC：
看子任务完成到了什么程度
```

这对于长程任务尤其有用。因为在复杂环境中，模型可能没有完全完成任务，但已经表现出一定的目标搜索、路径规划或跟随能力。

例如：

| 现象 | CSR | SGC |
| --- | --- | --- |
| 没有接近目标 | 低 | 低 |
| 接近目标但没满足完成条件 | 低 | 中等或较高 |
| 多个子任务都基本完成 | 高 | 高 |

SGC 可以帮助分析模型失败的程度，而不是只给出二值成功或失败。

## OSR：Oracle Success Rate

OSR 是 Oracle Success Rate，表示 agent 在执行过程中是否曾经到达过目标附近。

它和 SR 的区别在于：

```text
SR：
要求 agent 最终正确停止并满足成功条件

OSR：
只要 agent 曾经到达过目标附近，就可能记为成功
```

因此，OSR 可以用来判断模型是否具备到达目标的能力，但可能缺少正确停止或任务完成判断能力。

例如：

```text
agent 曾经走到目标附近
但没有停止
或者又离开了目标区域
```

这种情况下，OSR 可能较高，但 SR 仍然较低。

如果一个模型出现：

```text
OSR 明显高于 SR
```

通常说明模型并不是完全不会导航，而是可能存在：

```text
停止判断不稳定
任务完成检测不准确
子任务切换时机错误
目标附近行为不稳定
```

所以，OSR 和 SR 通常需要一起看。SR 更严格，OSR 更能反映模型是否曾经接近正确答案。

## SPL：Success weighted by Path Length

SPL 是 Success weighted by Path Length，用来衡量成功任务中的路径效率。

一个 agent 即使完成任务，也可能走了很长的绕路。SPL 就是用来衡量：

```text
agent 是否以较短路径完成任务
```

它可以理解为：

```text
成功率 + 路径长度惩罚
```

如果 agent 成功到达目标，并且路径接近最短路径，SPL 会较高；如果 agent 虽然成功了，但绕路很多，SPL 会下降。

例如：

| 情况 | SR | SPL |
| --- | --- | --- |
| 成功且路径短 | 高 | 高 |
| 成功但路径很长 | 高 | 较低 |
| 没有成功 | 低 | 低 |

SPL 的作用是避免只追求“最终到达”，而忽略路径质量。

在具身导航中，路径效率很重要。真实机器人如果频繁绕路，不仅耗时更长，也可能增加碰撞、迷失或干扰人类活动的风险。

## HFS：Human Follow Success

HFS 是 Human Follow Success，用于衡量 Human Following 任务最终是否成功。

Human Following 和静态目标导航不同，因为目标人会移动。Agent 需要持续观察目标，并在合适距离内跟随。

HFS 关注的是：

```text
在跟随阶段结束时，agent 是否仍然成功跟随目标人
```

也就是说，它更强调最终状态是否满足跟随要求。

例如：

```text
目标人停止移动时
agent 是否仍在合理距离内
agent 是否朝向目标人
agent 是否没有丢失跟随对象
```

HFS 是一个较严格的结果指标。如果 agent 中途跟得不错，但最后丢失目标，HFS 仍然可能失败。

## HFR：Human Follow Ratio

HFR 是 Human Follow Ratio，用来衡量 agent 在跟随阶段中有多长时间保持了有效跟随状态。

它和 HFS 的区别是：

```text
HFS：
看最终是否跟随成功

HFR：
看整个跟随过程中有多少比例是有效跟随
```

例如，一个 agent 在 100 个时间步中有 70 个时间步保持了合理跟随状态，那么 HFR 就会较高。

HFR 可以反映跟随过程的稳定性。

| 情况 | HFS | HFR |
| --- | --- | --- |
| 一直稳定跟随并最终成功 | 高 | 高 |
| 中途大部分时间跟随成功，但最后失败 | 低 | 较高 |
| 只在最后一刻接近目标 | 可能高 | 较低 |
| 全程频繁丢失目标 | 低 | 低 |

因此，HFS 和 HFR 需要结合阅读。HFS 更关注结果，HFR 更关注过程。

## EQA-ACC：Embodied Question Answering Accuracy

EQA-ACC 是 Embodied Question Answering Accuracy，用于衡量 agent 在具身问答任务中的回答准确率。

EQA 和普通视觉问答不同。普通视觉问答通常给定一张图像，然后让模型回答问题；而 EQA 中，agent 可能需要先在环境中移动，主动寻找能够回答问题的视觉信息。

例如：

```text
Question:
Is there a lamp beside the sofa?

Agent needs to:
进入相关区域
-> 观察 sofa 附近
-> 判断是否存在 lamp
-> 输出答案
```

EQA-ACC 衡量的是最终回答是否与标准答案匹配。

这个指标反映的不只是语言生成能力，还包含：

```text
是否移动到合适位置
是否观察到关键信息
是否理解问题
是否能从视觉信息中得到答案
```

如果 EQA-ACC 低，可能不一定是模型不会回答问题，也可能是它根本没有导航到能观察答案的位置。

因此，在分析 EQA-ACC 时，需要结合导航轨迹一起看。

## SII：Social Intrusion Index

SII 是 Social Intrusion Index，用于衡量 agent 在有人类活动的场景中是否侵犯了人的个人空间。

它关注的是：

```text
agent 在执行过程中，有多少时间步过度接近人类
```

和其他多数指标不同，SII 是越低越好。

如果 SII 较高，说明 agent 可能频繁靠近人类，造成不安全或不自然的交互行为。

例如：

```text
从人面前突然穿过
长时间贴近行人移动
阻挡人的路线
在跟随任务中距离过近
```

这些行为即使没有发生碰撞，也可能被认为是不合适的导航行为。

SII 的意义在于，它把导航评测从“是否到达目标”扩展到了“是否以合适方式到达目标”。在真实机器人应用中，这一点非常关键。

## 指标之间的组合阅读

单个指标只能反映某一方面能力。阅读 OmniNavBench 结果时，更重要的是把多个指标结合起来看。

### SR 低，SGC 高

这种情况说明 agent 没有完整完成任务，但在子任务层面取得了一定进展。

可能原因包括：

```text
能完成前几个阶段，但后续任务失败
能接近目标，但没有满足严格完成条件
长程任务中出现累积误差
子任务切换不稳定
```

这种模型并不是完全无效，而是可能需要改进长程规划、停止判断或任务管理能力。

### OSR 高，SR 低

这种情况说明 agent 曾经到达过目标附近，但没有最终成功。

可能原因包括：

```text
没有及时停止
到达目标后又离开
没有正确判断任务完成
最终阶段动作不稳定
```

这类问题常见于缺少可靠终止判断的导航策略。

### SR 高，SPL 低

这种情况说明 agent 虽然能完成任务，但路径效率较差。

可能原因包括：

```text
探索过多
绕路严重
局部路径规划不稳定
对环境结构理解不足
```

这类模型具备一定成功能力，但执行成本较高。

### HFR 高，HFS 低

这种情况说明 agent 在跟随过程中大部分时间表现不错，但最终状态失败。

可能原因包括：

```text
最后阶段丢失目标
目标停止时 agent 没有及时调整位置
结束条件判断不准确
```

这类问题适合通过分析跟随阶段的视频或轨迹进一步定位。

### EQA-ACC 低

EQA-ACC 低可能来自两个层面：

```text
导航阶段失败：
agent 没有移动到能看到答案的位置

问答阶段失败：
agent 看到了相关信息，但没有正确理解或回答
```

因此，EQA-ACC 不应该孤立阅读，需要结合轨迹和视觉观测判断具体原因。

### SII 高

SII 高说明 agent 在有人的场景中存在安全或社交问题。

可能原因包括：

```text
只追求到达目标，忽略人类位置
缺少社交距离约束
动态避让能力不足
跟随任务中过度接近目标人
```

在真实机器人应用中，即使 SR 较高，如果 SII 也很高，方法仍然可能不适合部署。

## Baseline 方法

OmniNavBench 使用多个已有统一导航方法作为 baseline，用来观察当前方法在组合式导航、跨形态和动态交互环境中的表现。论文中比较了 MTU3D、PoliFormer、Uni-NaVid 和 OmniNav，并采用公开权重进行 zero-shot 评测，只根据不同算法需求调整相机数量、分辨率和视场角等输入设置。:contentReference[oaicite:1]{index=1}

这些 baseline 可以大致理解为四类不同思路。

| 方法 | 基本思路 | 主要特点 |
| --- | --- | --- |
| MTU3D | 统一导航与探索 | 更强调通过移动获取空间理解 |
| PoliFormer | 基于 transformer 的强化学习导航方法 | 试图从多任务训练中学习通用导航行为 |
| Uni-NaVid | 将导航任务统一为视觉-语言-动作生成问题 | 更适合处理 egocentric video 和语言条件导航 |
| OmniNav | 使用共享 waypoint 表示统一多种导航任务 | 更强调通过连续 waypoint 抽象连接不同任务形式 |

这些方法都试图在一定程度上统一多种导航任务，但 OmniNavBench 的组合式 episode 对它们提出了更高要求。

## MTU3D

MTU3D 可以理解为一种强调导航与空间理解结合的方法。它不只是让 agent 到达目标，也关注 agent 如何通过移动获得环境信息。

这类方法适合处理需要主动探索的导航问题。例如，agent 在一开始看不到目标物体，就需要通过移动扩大观察范围。

在 OmniNavBench 中，MTU3D 可以用于观察：

```text
空间探索能力是否足够
能否在复杂环境中找到目标区域
面对组合任务时是否能保持长期目标
是否能处理动态人类相关任务
```

如果 MTU3D 在 SGC 上有一定表现，但 SR 较低，通常说明它能在部分子目标上取得进展，但还难以稳定完成完整组合指令。

## PoliFormer

PoliFormer 是基于 transformer 的导航策略方法，主要通过强化学习或策略建模来学习跨任务导航行为。

这类方法的特点是希望通过统一策略处理不同任务，而不是为每个任务单独设计规则。

在 OmniNavBench 中，PoliFormer 可以用于观察：

```text
统一策略是否能适应组合式导航
transformer 策略是否能处理长程状态
面对不同机器人形态时是否稳定
面对语言变化时是否鲁棒
```

如果方法在某些单任务中表现尚可，但在组合任务中 SR 较低，说明它可能缺少稳定的任务分解、阶段切换或长期记忆能力。

## Uni-NaVid

Uni-NaVid 将导航任务统一成视觉、语言和动作之间的生成问题。它通常更依赖第一人称视觉输入和语言条件信息。

这种方法适合处理视觉语言导航相关任务，因为它能够将 egocentric video、语言指令和动作输出放到统一框架下。

在 OmniNavBench 中，Uni-NaVid 可以用于观察：

```text
视觉语言模型能否处理组合式导航指令
egocentric video 是否足以支持长程任务
模型是否能适应不同语言表达
在 EQA 相关任务中是否具备一定优势
```

如果 Uni-NaVid 在部分语言相关指标上表现较好，但在 SII 或 Human Following 上表现不稳定，说明视觉语言统一建模并不自动解决动态交互和安全距离问题。

## OmniNav

OmniNav 使用共享 waypoint 表示来统一多种导航任务。Waypoint 可以看作高层导航目标，比底层动作更抽象。

这种设计有利于连接不同任务形式：

```text
VLN 可以输出下一步导航点
ObjectNav 可以输出接近目标物体的 waypoint
PointNav 可以直接对应目标位置
Human Following 可以不断更新跟随目标附近的 waypoint
```

在跨机器人形态场景中，waypoint 表示也更自然。不同机器人可以使用自己的低层控制器去跟踪相同的高层目标点。

在 OmniNavBench 中，OmniNav 可以用于观察：

```text
共享 waypoint 表示是否能统一多类任务
高层导航目标是否有利于跨形态迁移
组合任务中 waypoint 是否能稳定连接多个阶段
动态人类和社交约束是否会破坏 waypoint 跟踪效果
```

如果 OmniNav 在某些机器人形态上表现更好，但换形态后性能下降，说明高层表示虽然有助于统一任务，但仍然受到机器人视角、控制和环境分布的影响。


## 指标与任务能力的对应关系

可以把指标和能力之间的关系整理如下：

| 能力 | 相关指标 | 阅读重点 |
| --- | --- | --- |
| 完整长程执行 | SR | 是否能完成整条组合指令 |
| 阶段性任务完成 | CSR、SGC | 是否能完成中间子目标 |
| 目标接近能力 | OSR | 是否曾经到达目标附近 |
| 路径效率 | SPL | 是否用较短路径完成任务 |
| 动态跟随 | HFS、HFR | 是否能稳定跟随移动目标 |
| 环境问答 | EQA-ACC | 是否能观察并回答场景问题 |
| 社交安全 | SII | 是否避免过度接近人类 |
| 跨形态泛化 | 不同机器人上的全部指标 | 是否依赖特定机器人身体 |

这个对应关系可以帮助读者从表格中反推出模型的能力短板。

例如：

```text
SR 低，SGC 高
-> 长程衔接问题

OSR 高，SR 低
-> 停止判断或完成检测问题

HFR 低
-> 动态目标跟随问题

SII 高
-> 社交安全问题

EQA-ACC 低
-> 主动观察或视觉问答问题
```

## 结果比较时需要统一条件

在比较 baseline 时，需要确认实验条件是否一致。导航 benchmark 中，很多因素都会影响结果：

```text
使用的环境划分
机器人形态
传感器配置
相机视角和分辨率
语言指令风格
是否使用相同初始位置
是否 zero-shot 评测
是否使用额外训练数据
```

如果这些设置不同，指标之间就不一定能直接比较。

例如：

```text
一个方法使用 RGB-D
另一个方法只使用 RGB
```

这时结果差异可能来自模型能力，也可能来自输入信息差异。

再比如：

```text
一个方法在轮式机器人上测试
另一个方法在四足机器人上测试
```

这时不能直接说前者或后者更强，因为机器人形态本身会改变任务难度。

因此，阅读 OmniNavBench 的 baseline 表格时，需要先确认：

```text
是否是同一任务划分
是否是同一机器人形态
是否是同一传感器设置
是否是同一语言指令形式
```

只有在条件一致时，指标比较才更有意义。

## 本节内容回顾

OmniNavBench 的评测体系围绕组合式导航展开。SR 衡量整条任务是否完成，CSR 和 SGC 衡量子任务完成情况，OSR 判断 agent 是否曾经到达目标附近，SPL 衡量路径效率，HFS 和 HFR 衡量 human following，EQA-ACC 衡量具身问答，SII 衡量社交安全。

这些指标共同构成了一个多维评测框架。通过它们可以判断模型失败的具体原因：是基础导航能力不足，还是任务切换失败；是目标已经接近但没有停止，还是路径效率太低；是能完成任务但行为不安全，还是面对动态人类和问答任务时表现不稳定。
