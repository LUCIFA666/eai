# 模型资产与本体描述

目标：理解机器人模型文件如何描述本体结构，并知道这些描述如何被仿真器、控制栈、数据集和策略接口共同使用。

## 模型资产在系统中的作用

在具身智能系统的整个生命周期中，机器人模型文件并不是一个仅在仿真阶段才用到的"3D 模型"。它实际上是贯穿多个子系统的**共同信息源**。具体来说，模型资产在以下六个环节中扮演关键角色：

### 可视化

模型文件中的几何信息定义了每个连杆的外观形状、尺寸、颜色和材质。无论是 RViz 中的实时状态显示，还是仿真器中的渲染画面，都依赖这些几何数据来呈现机器人的当前姿态。更重要的是，可视化不仅服务于开发者调试 —— 在 teleoperation（遥操作）场景下，操作员也需要通过可视化界面判断机器人状态。

### 碰撞检查

模型文件中的碰撞几何体通常与视觉几何体分开定义。碰撞几何体使用简化形状（如球体、圆柱体、盒体或凸包），因为精确的三角网格碰撞检测计算量过大，无法在实时控制循环中运行。运动规划算法（如 MoveIt 使用的 OMPL）在搜索无碰撞路径时，依赖的正是这些简化的碰撞几何。

### 运动学查询

模型文件定义了所有关节的类型（revolute、prismatic、fixed 等）和它们之间的父子连接关系，从而构成一棵**运动学树**。正运动学（给定关节角度，求末端位姿）和逆运动学（给定目标位姿，求关节角度）都依赖这棵树的拓扑结构和几何参数。`pinocchio`、`KDL` 等运动学库从模型文件加载运动学链后进行高效计算。

### 仿真加载

仿真器（MuJoCo、Isaac Sim、SAPIEN、PyBullet 等）在初始化仿真场景时，直接读取模型文件来构建物理世界。模型中的质量、惯性张量、关节阻尼、摩擦系数等物理参数决定了仿真中的动力学行为。如果这些参数缺失或不准确，仿真结果将与真实机器人行为产生偏差，进而影响 sim-to-real transfer 的效果。

### 控制接口生成

模型文件中定义的关节名称、数量、类型和限位，直接决定了控制接口的格式。例如，若模型定义了 7 个 revolute 关节和 2 个 prismatic 关节（夹爪），则控制接口期望接收长度为 9 的命令向量，且前 7 个为角度（rad）、后 2 个为开合量（m）。`ros2_control` 框架根据模型文件自动生成对应的 hardware interface 和 controller 配置。

### 数据字段对齐

在数据采集、策略训练和真机部署三个阶段，模型文件充当**字段命名的唯一事实来源**。状态数据中的 `joint_names`、命令消息中的关节顺序、日志中的传感器 frame_id，全部应与模型文件中的定义一致。一旦模型文件版本变更（例如升级了末端执行器），所有下游的字段引用都需要同步对齐。

## 模型资产的基本组成

机器人模型文件无论是 URDF（Unified Robot Description Format）还是 MJCF（MuJoCo XML Format），其核心元素是相通的。以下按字段逐一说明。

### link —— 连杆

link 是机器人模型中最基本的刚体单元，代表一个不可变形的物理部件。每个 link 包含以下子元素：

- **visual**：用于渲染的外观几何体，可以是基本形状（box、cylinder、sphere）或导入的 mesh 文件（STL、OBJ、DAE）。
- **collision**：用于碰撞检测的简化几何体，通常比 visual 更简单。
- **inertial**：质量、质心位置和惯性张量矩阵，是动力学计算的必要输入。

一个典型的机械臂由多个 link 串联组成，例如 base_link → shoulder_link → upper_arm_link → forearm_link → wrist_link → gripper_link。

### joint —— 关节

joint 定义两个 link 之间的连接关系和运动约束。关键属性包括：

- **type**：关节类型，常见的有 `revolute`（旋转关节，有角度限位）、`continuous`（无限旋转关节）、`prismatic`（平移关节）、`fixed`（固定连接，无自由度）、`floating`（六自由度浮动关节，常用于移动底盘）。
- **parent / child**：指定关节连接的两个 link，parent 为上级连杆，child 为下级连杆。
- **origin**：定义 child link 坐标系相对于 parent link 坐标系的初始变换（平移 + 旋转），即关节在零位时的相对位姿。
- **axis**：关节的运动轴方向，在 parent link 坐标系中表达。
- **limit**：关节的运动范围限制，包括位置上下限（`lower` / `upper`）、速度上限（`velocity`）和力矩上限（`effort`）。

在 URDF 中，joint 定义了运动学树的边；在 MJCF 中，关节概念与 actuator 解耦，关节定义运动约束，actuator 定义驱动方式。

### actuator —— 执行器/驱动器

actuator 将关节与驱动力关联起来。在 URDF 中，执行器信息通常通过 `<transmission>` 标签或由 `ros2_control` 的配置文件补充；在 MJCF 中，`<actuator>` 标签明确定义了每个关节的驱动类型：

- **position**：位置驱动，直接控制关节角度（理想位置伺服）。
- **velocity**：速度驱动，控制关节角速度。
- **motor**：力矩驱动（电机模型），可配置齿轮比和力矩上限。
- **general**：通用驱动，可同时作用于多个关节（如腱驱动）。

actuator 的定义直接影响控制接口的设计 —— 哪些关节支持力矩控制、哪些只支持位置控制，这些信息来自 actuator 而非 joint 本身。

### geometry —— 几何体

geometry 描述 link 的三维形状，通常出现在 visual 和 collision 子元素中。常见形式包括：

- **基本形状**：box（长方体，指定长宽高）、cylinder（圆柱体，指定半径和高度）、sphere（球体，指定半径）。
- **mesh**：引用外部三维模型文件（STL、OBJ、DAE），通过 `filename` 指定路径，通过 `scale` 调整尺寸。

geometry 本身不包含材质信息，材质通过 material 子元素单独指定。

### collision —— 碰撞几何

collision 用于物理引擎的碰撞检测。其 geometry 子元素通常比 visual 更简化，原因是在实时仿真中，三角面片级别的碰撞检测计算成本极高。典型做法是：

- 用几个圆柱体近似一个复杂形状的连杆。
- 用凸包近似一个凹形零件。
- 去掉对碰撞无关紧要的细节（螺丝孔、装饰凹槽等）。

collision 的可选属性 `group` 和 `mask` 用于精细控制哪些 link 之间会发生碰撞 —— 例如，相邻关节的 link 通常被排除在碰撞检测之外，因为它们本就紧密接触。

### inertial —— 惯性参数

inertial 元素为 link 提供动力学计算所需的物理参数：

- **mass**：质量（kg），必须大于零，否则仿真物理将出错。
- **origin**：质心相对于 link 坐标系的位置和姿态。
- **inertia**：3×3 惯性张量矩阵的六个独立分量（`ixx`、`iyy`、`izz`、`ixy`、`ixz`、`iyz`），相对于质心坐标系表达。

惯性参数对动力学仿真的逼真度有直接影响。在仿真中训练的策略如果要迁移到真机，惯性参数必须尽可能准确。缺失的惯性参数通常通过 CAD 软件自动计算或通过系统辨识实验获得。

### sensor mount —— 传感器挂载点

传感器在模型文件中有两种表达方式：

- **独立的 link**：将传感器定义为带有 visual 几何的独立 link，通过 fixed joint 固定在父 link 上。这种方式最直观，方便可视化调试。
- **sensor 标签**：URDF 的 `<sensor>` 扩展（或 MJCF 的 `<sensor>` 标签）直接定义传感器的类型、参数和挂载位置，不额外创建 link。

无论哪种方式，关键的工程信息是传感器在哪个 frame 下、朝向哪个方向、数据以什么格式输出。这些信息在第 3 节"空间关系与坐标约定"和第 4 节"机器人状态观测"中会详细展开。

### end-effector —— 末端执行器

末端执行器是机器人与操作对象交互的终端部件，包括夹爪、吸盘、灵巧手等。在模型文件中，末端执行器表现为运动学链的最末端一个或几个 link。其关键特征包括：

- **mounting frame**：末端执行器安装在哪个 link 上（通常是腕部的 tool flange），有一个明确的安装位姿。
- **grasp frame**：抓取中心点所在的坐标系，是规划算法计算抓取位姿的参考。
- **独立自由度**：夹爪的左右指关节、吸盘的气阀状态等，在控制命令中作为独立字段出现。

末端执行器的模型定义直接决定了第 6 节的接口设计 —— 抓取命令的格式、状态反馈的字段，都从这里开始。

### material —— 材质

material 定义 link 的视觉外观，用于渲染而非物理仿真。可指定的属性包括颜色（RGBA）、纹理贴图（texture filename）和光照参数。material 仅影响可视化，不影响碰撞、动力学或控制接口。在 MJCF 中，材质还可以通过 `<asset>` 中的 `<material>` 和 `<texture>` 标签定义更丰富的表面属性。

## 为什么模型文件不只是渲染文件

许多开发者第一次接触机器人模型时，容易把它理解为一个"3D 显示文件"—— 类似于游戏中的角色模型。但在具身智能系统中，模型文件的角色远比这重得多。可以将它理解为一个**结构化的元数据库**，至少同时服务于以下五类消费者：

| 消费者 | 从模型文件中读取什么 | 用途 |
|--------|---------------------|------|
| 运动学求解器 | joint 类型、origin、axis、运动学树拓扑 | 计算正/逆运动学 |
| 物理仿真器 | mass、inertia、collision geometry、joint damping/friction | 计算动力学响应 |
| 控制框架 | joint 名称、数量、类型、limit、actuator 配置 | 生成控制接口和 hardware interface |
| 规划算法 | collision geometry、joint limit、运动学链 | 碰撞检测和无碰撞路径搜索 |
| 数据/策略接口 | joint_names、frame_id、坐标变换链 | 定义状态和动作的字段 schema |

因此，模型文件的一个字段错误 —— 比如某个 joint 的 axis 方向填反、inertial 的 mass 设为零、collision geometry 偏移了 2cm —— 可能导致以下连锁故障：

- 运动学解算结果错误，末端始终到不了目标位姿。
- 仿真中的动力学行为异常，训出的策略无法迁移真机。
- 规划算法认为某条路径无碰撞，实际运行时却撞上障碍物。
- 控制命令的关节顺序与状态数据的关节顺序不一致，策略给第 3 关节发的命令被第 4 关节执行。

**模型文件是机器人系统中信息密度最高的单一文件**，它的准确性直接影响整个具身智能管线的可靠性。

## 本节范围与平台差异

本节聚焦于模型文件的**格式语义和字段含义**，目标是让读者具备以下能力：

- 打开一个 URDF 或 MJCF 文件后，能理解每个字段的作用。
- 知道一个规范的模型文件应该包含哪些必要信息。
- 能在不同平台之间建立字段的对应关系。

本节**不涉及**以下内容：

- 各仿真平台的导入教程和操作步骤。
- 具体仿真器的 GUI 配置界面使用方法。
- 模型文件的创建（从 CAD 导出、通过 SolidWorks-to-URDF 插件生成等）。

MuJoCo、Isaac Sim、SAPIEN、PyBullet、CoppeliaSim 等仿真平台在模型导入、物理参数设置、传感器插件等方面存在较大差异，这些内容统一放到第 5 章"仿真平台"中展开。届时会以本章的字段定义为基础，说明每个平台分别如何映射这些字段，帮助读者在跨平台迁移时快速对齐。

## 典型机器人平台示例

在后续章节中，状态观测、动作命令、坐标约定等内容需要以具体机器人作为实例进行说明。以下是具身智能领域当前常用的典型平台，作者在撰写后续内容时应优先以这些机器人为例：

### 机械臂平台

- **Franka Emika Panda / FR3**：7 自由度力控机械臂，带二指夹爪，具备关节力矩传感和 Cartesian 导纳控制接口。在具身智能研究中广泛使用，是 RL 和 imitation learning 最常用的硬件平台之一。
- **Universal Robots (UR5 / UR5e / UR10)**：6 自由度机械臂，工业级可靠性高，支持多种末端执行器安装。控制接口通过 UR 驱动或 `ur_robot_driver` 暴露，生态成熟。
- **xArm 系列 (UFACTORY xArm 5/6/7)**：性价比高的轻量级机械臂，支持位置、速度和力矩控制模式，Python SDK 友好，在学术实验室中非常普及。
- **KUKA LBR iiwa / LBR iisy**：7 自由度力控机械臂，关节力矩传感器精度高，适用于力控装配和精细操作，但价格较高。

### 移动操作平台

- **Hello Robot Stretch (RE1/RE2/RE3)**：专为家庭和实验室环境设计的低成本移动操作平台。底座为差速驱动的移动底盘，配有一个伸缩臂和一个末端夹爪，附带相机和 IMU。URDF 模型公开，ROS 2 支持完善。
- **Unitree 系列**：包括四足机器人（Go2、B2）和人形机器人（H1、G1）。模型文件公开，仿真支持完善，是 locomotion 和 whole-body control 的常见研究平台。
- **Boston Dynamics Spot**：四足机器人，通过官方 SDK 控制。模型资产受限于 API 层，但可作为理解"闭源 SDK 封装下的接口认知"的案例。

### 末端执行器

- **Robotiq 2F-85 / 2F-140**：二指自适应夹爪，通过 Modbus RTU 或 UR 接口通信，支持位置、速度和力控抓取。
- **Schunk 系列**：包括平行夹爪和灵巧手（SVH），力控精度高，广泛应用于精细操作。
- **Robotiq EPick / Piab 吸盘**：气动真空吸盘，用于 pick-and-place 任务，通过数字 IO 或 Modbus 控制气阀。

在撰写后续章节的示例时，应尽量复用这些常见平台的名称和结构，减少读者在平台细节上的认知负担，让注意力聚焦在接口概念本身。
