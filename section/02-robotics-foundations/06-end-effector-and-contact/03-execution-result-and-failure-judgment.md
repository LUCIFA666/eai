# 执行结果与失败判定

机器人执行完一个动作之后，策略需要知道结果——成功了还是失败了？如果失败了，是什么原因？但"成功"本身是一个模糊的概念。抓取任务中，夹爪闭合后物体可能被牢固夹持（成功），也可能根本没有碰到物体（空抓），还可能夹住了但随后滑落（部分成功/失败）。如果只返回一个 success/failure 布尔值，策略无法分辨这三种情况，也就无法做出不同的后续处理。

因此，在机器人接口设计中，执行结果的反馈需要结构化、可区分，并且附带判定依据。策略需要基于具体的状态信号和判定阈值来判断执行结果，而不是依赖一个黑盒的"成功"标志。

本节定义执行结果的状态字段，介绍末端执行常见的判定信号，讨论不同任务类型对成功标准的不同要求，列出可区分的失败类型，并强调日志中记录判定依据的重要性。本节不涉及视觉评测指标和 benchmark 评分规则，这些内容将在第 8 章评测工程中讨论。

## 执行结果的状态字段

一个结构化的执行结果不应只是一个布尔值，而应使用能够表达不同程度和不同原因的状态枚举。以下是执行结果反馈的推荐字段定义：

```text
execution_result:
  status: "success" | "partial_success" | "failed" |
          "aborted" | "timeout" | "unsafe" | "unknown"
  failure_reason: "no_object_detected" | "slip_detected" |
                  "force_limit_exceeded" | "collision" |
                  "target_unreachable" | "controller_rejected" |
                  "sensor_fault" | null
  confidence: 0.92            # 判定可信度 (0~1)
  detail:                     # 判定依据
    gripper_closed_width: 0.042
    expected_object_width: 0.045
    force_achieved: 8.3
    target_force: 10.0
    slip_detected: false
    time_elapsed: 2.3
  timestamp: 1723001235.200
```

各状态值的含义为：

- **success**：动作完全按预期完成，所有关键指标均满足成功标准。例如抓取任务中：夹爪闭合到目标宽度附近、夹持力达到设定值、未检测到滑移、物体已被提升离开支撑面。

- **partial_success**：动作部分完成，但未达到全部成功标准。例如物体被抓取并提起，但夹持力低于目标值（可能不够稳固）；又如插入任务中，物体插入了一半但未完全就位。partial_success 提示策略——任务的基础目标达成了，但质量不够理想，可能需要微调或重新尝试。

- **failed**：动作执行失败，但失败原因可识别。failed 必须伴随 failure_reason 字段，说明失败的具体原因（空抓、滑落、力超限等）。有原因的失败比静默的失败更有价值，因为它告诉策略"为什么失败"，而不是只告诉策略"你失败了"。

- **aborted**：动作因外部原因被中止，例如急停被触发、更高优先级任务抢占当前执行、或者人工操作员介入。aborted 不表示策略输出有误，而表示外部条件发生了变化，策略应等待恢复正常后重新尝试或调整计划。

- **timeout**：动作在预设的时间限制内未能完成。例如，机器人向目标位置运动了 5 秒仍未到达（可能因为目标不可达、速度设置过低或关节被卡住）。timeout 提示策略应检查是否设定了不合理的时间预算或目标。

- **unsafe**：动作在执行过程中触发了安全保护（力超限、碰撞检测、关节力矩过大等），但尚未发生实际损坏。unsafe 是介于 failed 和 aborted 之间的一种状态——它不是因为任务逻辑错误而失败，也不是被外部命令中止，而是因为安全边界被触碰。unsafe 结果要求策略在继续之前降低动作的激进程度。

- **unknown**：无法确定执行结果。例如传感器故障导致无法读取关键判定信号，或者判定逻辑的输入数据完整性不足。unknown 应触发策略进入保守模式，不应假设任务已成功。

## 末端执行常见判定信号

判断末端执行是否成功，不是依赖某一个信号，而是综合多个传感器信号和状态字段。以下是常见的判定信号及其在不同任务中的解读方式。

**夹爪宽度变化（Gripper Width Change）**是最直接的抓取判定信号。当夹爪向闭合方向运动时，如果实际宽度在到达空载闭合宽度之前就停止了变化，说明手指遇到了物体——有东西被夹住了。但如果夹爪闭合到空载宽度（即手指完全靠拢）仍未遇到阻力，则是**空抓（Missed Grasp）**——手指从物体旁边划过，根本没有碰到物体。

**力/压力阈值（Force / Pressure Threshold）**是比宽度更可靠的接触判定依据。即使手指触碰到了物体，如果夹持力未达到设定的目标值，抓取仍然不稳固。力反馈的优势在于它直接反映接触质量，不受物体形状影响——一个不规则形状的物体可能让夹爪在较大宽度时就产生接触力，此时宽度信号的意义下降，应更依赖力信号。

**接触检测（Contact Detected）**信号来自力传感器、触觉阵列或接近传感器。对于吸盘，接触检测与气压的下降同步；对于夹爪，接触检测通常在夹持力开始上升的时刻触发。接触信号的时序——相对于动作命令发出时刻的时间差——也是判断执行是否正常的重要线索。如果接触发生在预期时间窗口之外，可能意味着物体位置与策略的估计不符。

**物体运动（Object Motion）**是最直接的抓取成功信号，但通常需要外部感知（相机、激光雷达或外部跟踪系统）才能获取。在抓取任务中，物体随末端一起运动说明了抓取的成功。但此信号有延迟：物体从静止到运动有一个加速过程，传感器从检测到物体运动到反馈给策略也有延迟。因此，物体运动信号更适合作为事后的成功确认，而不是实时的控制反馈。

**滑移检测（Slip Detected）**用于判断物体在夹持状态下是否发生了不希望的位置偏移。滑移的信号来源包括：切向力突然下降（静摩擦到滑动摩擦的转变）、触觉阵列上的接触区域漂移、或物体相对于夹爪的视觉位置变化。滑移一旦被检测到，即使夹持力仍然存在，也应判定为抓取质量下降或即将失败。

**控制器状态（Controller Status）**是判断执行是否遇到硬件或底层问题的关键信号。如果控制器返回 fault、limit exceeded 或 tracking error过大，即便末端位置看起来"接近目标"，也应该判定为执行异常。控制器状态是系统级健康信号，优先级高于任务级成功标准——控制器异常意味着底层系统可能已不稳定，不应再信任任何任务级的判定结果。

## 不同任务类型的成功标准

不同的机器人任务对"成功"的定义完全不同。以下列举具身智能常见的任务类型及其对应的成功标准组合。

**抓取（Grasping）**的成功通常需要同时满足：夹爪（或吸盘）与物体建立有效接触、夹持力（或吸附力）达到设定阈值、物体可以被提升离开支撑面、提升过程中未检测到滑移、放置到目标位置时物体稳定释放。仅夹爪闭合到某宽度或仅检测到接触力，不足以判定抓取成功。

**放置（Placing）**的成功标准包括：末端执行器到达目标放置位置、物体与支撑面发生接触（通过力反馈或末端位置与桌面高度比较判断）、夹爪张开后物体未随夹爪回退移动（说明物体已释放）、物体在支撑面上稳定（未滚落或翻倒）。如果物体在释放后倒下或滚落，则属于 partial_success 或 failed，取决于任务对放置姿态的精度要求。

**按压（Pressing）**关注的是力而不是位置。成功的按压需要满足：末端到达按压力目标值（或接触面位移达到目标深度）、力在目标值附近保持稳定、未出现力的异常尖峰或突然下降。在按压任务中，位置误差的容忍度通常比自由空间运动更大——只要力达到了目标，位置可以偏离标称值。

**推动（Pushing）**的成功标准包含两个层面：接触层面——末端与物体保持持续接触且未滑脱；运动层面——物体沿预期方向移动了足够的距离。推动任务的接口判定通常需要结合末端力反馈（接触是否持续）和外部物体运动跟踪（物体是否移动）两个信号源。

**插入（Insertion）**是接触任务中对精度要求最高的类型之一。成功的插入需要末端沿插入方向推进到目标深度、插入过程中力不超过安全阈值（过大表示卡滞或错位）、插入后物体稳定在位（不会被回弹推出）、且插入过程的时间在合理范围内。插入任务中，depth_achieved 与 depth_target 的比值是一个重要的量化指标——插入 80% 可能被判定为 partial_success，插入 100% 才是 success。

**开门（Door Opening）**涉及机器人与可动机构的交互。成功的开门需要：末端与门把手建立稳定接触（抓取或勾住）、门沿铰链轴线方向旋转到目标角度、旋转过程中末端未从把手上滑脱、门的运动阻力在机器人能力范围内（未触发力保护）。开门的独特之处在于成功标准既取决于机器人本身（是否抓住把手），也取决于环境（门是否被卡住或太重）。

**工具使用（Tool Usage）**的成功标准取决于具体工具的功能。例如，使用螺丝刀拧紧螺丝需要螺丝头完全就位且扭矩达到设定值；使用焊枪焊接需要焊点温度达到目标温度且持续时间达标。工具使用通常需要工具自身提供专门的反馈信号（如扭矩传感器、温度传感器、激光功率计等），通用末端状态字段不足以完整描述其成功条件。

不同任务需要不同的判定信号组合，这意味着执行结果的接口设计不能对所有任务使用同一组固定字段。接口应允许任务层声明其关注的状态组合和判定阈值——例如抓取任务声明关注 gripper_width + contact_force + slip，插入任务声明关注 insertion_depth + contact_force + time。

## 失败类型的可区分性

执行失败本身没有足够的信息量——策略需要知道"为什么失败"，才能决定下一步怎么办。因此，失败类型必须是可区分的，每种失败类型对应不同的信号特征和恢复策略。

**空抓（Missed Grasp / Empty Grasp）**：夹爪闭合到空载宽度，未检测到有效接触力，物体仍停留在原位置。信号特征为夹爪宽度接近最小值但接触力接近零。恢复策略是调整抓取位姿后重试。

**滑落（Slip / Drop）**：物体在夹持后被提起，但在运动过程中从末端滑落。信号特征为滑移信号触发、接触力突然下降、物体脱离接触后末端力归零。恢复策略是返回拾取位置，调整夹持力或抓取姿态后重新抓取。

**卡住/卡滞（Jammed / Stuck）**：物体或末端在装配、插入或狭小空间中运动受阻。信号特征为位置变化接近零但力持续增大且未触发保护阈值。恢复策略是退让（沿运动反方向微动）、调整姿态后重新尝试，而不是继续增加力。

**碰撞（Collision）**：末端在运动过程中意外接触障碍物。信号特征为力或关节力矩突然跃升、可能触发碰撞保护或急停。恢复策略是停止当前运动，沿碰撞反方向退出，评估环境后重新规划路径。

**力超限（Force Exceeded）**：末端施加的力超过了任务或控制器的限制值。信号特征为力达到或超过限制阈值、可能伴随控制器告警或保护触发。恢复策略取决于超限的原因——如果是夹持力过大则减小目标力，如果是接触力超限则降低运动速度或调整接触策略。

**超时（Timeout）**：动作在预设时间限制内未完成。信号特征为时间超过 budget 但位置/力未达到目标。恢复策略取决于超时原因——可能是目标确实不可达（需更换目标）、速度设置过低（需提高速度）、或者被卡住（需退让重试）。

**目标不可达（Target Unreachable）**：期望位姿或关节角度因超出工作空间、关节限位或自碰撞约束而不可达。信号特征为 IK 求解失败、或控制器在接收到目标后立即拒绝。恢复策略是调整目标位姿至可行区域内。

**控制器拒绝（Controller Rejected）**：控制器主动拒绝了策略下发的命令。可能原因包括命令格式错误、关节角度超限、速度突变超过斜率限制、或控制器处于不允许接收新命令的状态（如 fault 或 e-stop）。信号特征为控制器返回拒绝码。恢复策略是检查命令合法性、确认控制器状态后再重新发送。

**传感器异常（Sensor Fault）**：用于判定执行结果的关键传感器数据缺失、超范围或明显不合理。信号特征为传感器返回错误码或数值在物理上不可能（如夹爪宽度为负值、力传感器满量程卡死）。恢复策略是进入安全状态，切换至备用传感器（如有）或降级为保守的开环控制，等待传感器恢复。

在接口实现中，这些失败类型应以枚举或错误码的形式定义，并由执行判定模块根据具体信号组合自动分类。策略不应自己去解析原始传感器数据来推断失败原因——这个推断逻辑应由接口层提供，策略接收的是已经结构化的失败类型。

## 日志中必须记录判定依据

仅记录一个 success 布尔值或一个失败枚举值，对于事后分析毫无帮助。当机器人抓取失败时，开发者需要知道的不只是"失败了"，而是：

- 夹爪闭合到什么宽度？
- 目标宽度是多少？
- 实际夹持力有多大？
- 力的目标值是多少？
- 是否检测到滑移？
- 力传感器的读数在整个执行过程中的变化趋势是什么？
- 哪个信号导致了失败判定？

因此，日志中必须记录完整的判定依据。一条典型的执行结果日志应包含：

```text
execution_log:
  task_id: "grasp_001"
  task_type: "grasp"
  timestamp_start: 1723001234.500
  timestamp_end: 1723001236.800
  status: failed
  failure_reason: "insufficient_force"
  detail:
    # 关键判定指标
    gripper_width:
      target: 0.045           # m
      actual: 0.048
      threshold_success: 0.050  # 闭合到 0.050 以内即认为接触到物体
      passed: true
    contact_force:
      target: 10.0            # N
      actual: 4.2
      threshold_success: 8.0  # 超过 8.0 N 即认为抓取牢固
      passed: false           # ← 失败判定依据
    slip:
      detected: false
      passed: true
    time_elapsed: 2.3         # s
    time_budget: 5.0          # s
    timeout: false
  robot_state:
    joint_positions: [...]
    ee_pose: [...]
    frame_id: "base_link"
  controller_status: "active"
```

日志中明确标注了判定依据的来源（contact_force 未达到 threshold_success），而不是只记录 `status: failed`。通过这种记录方式，开发者在事后分析时可以立即定位到问题所在，而不需要在大量原始数据中反向推断。

此外，判定阈值（如 target_force 和 threshold_success）也应一并记录，因为阈值本身可能在部署过程中被调整。如果只知道"力不够"而不知道当时的阈值是多少，就无法判断是力确实太小，还是阈值设得太高。

## 本节小结

执行结果的判定是机器人策略闭环的关键环节。单纯的成功/失败二元判断不足以支持策略做出有效的后续决策——策略需要知道失败的具体原因和判定依据。结构化的执行结果状态字段（success、partial_success、failed、aborted、timeout、unsafe、unknown）结合具体的 failure_reason 和判定详情，构成了从"机器人动了"到"策略知道发生了什么"的信息桥梁。

不同任务类型对成功的定义差异很大：抓取关注夹持力和滑移，插入关注深度和力，按压关注力而非位置，开门关注旋转角度和接触稳定性。执行结果的接口设计应允许任务层声明其关注的判定信号和阈值，而不是将所有任务的判定逻辑统一为固定的几个字段。

失败类型的可区分性是策略能够自适应恢复的前提——空抓需要调整位姿重试，滑落需要增加夹持力，卡滞需要退让后调整姿态，超时需要检查目标可达性和时间预算。最后，日志中必须记录完整的判定依据（实际值、目标值、阈值以及哪个信号触发了判定），使事后的故障排查从"猜测"转变为"追溯"。
