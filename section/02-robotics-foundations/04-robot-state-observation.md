# 机器人状态观测

目标：理解机器人运行时有哪些状态需要被观测、记录和回放，掌握状态数据的字段规范和质量要求，能够设计一套最小但完整的状态 schema。

## 状态观测在机器人系统中的作用

机器人运行时产生的状态数据，是整个具身智能系统中信息流密度最高的环节之一。与模型文件提供静态结构描述不同，状态观测提供的是**动态的、时变的、实时更新的**数据，反映机器人在每一时刻的真实情况。这些数据至少同时服务于三类消费者：

### 为策略提供本体感知输入

在具身智能中，策略（无论是 RL policy、imitation learning policy 还是 VLA 模型）需要持续的 proprioception 信息来感知机器人自身的状态。关节角度告诉策略机械臂的当前构型，末端位姿告诉策略手在哪里，基座速度告诉策略机器人在如何移动，力矩读数告诉策略当前受力情况。没有这些本体感知信息，策略就等同于"闭着眼睛控制自己的身体"——它不知道自己当前处于什么姿态，自然也无法决定下一步该怎么动。

除本体感知外，策略还需要 exteroception 信息（相机图像、深度图、点云等）来感知外部环境。本章聚焦于本体感知相关状态的观测接口，外部感知的传感器数据格式在第 3 章详细展开，本章只在传感器状态层面说明数据是否可用、是否可信。

### 为控制器提供实时反馈

控制器的核心工作是在一个闭环中运行：读取当前状态 → 计算与目标值的偏差 → 输出控制信号 → 等待下一个周期。这个闭环的输入，正是来自状态观测。如果状态数据延迟过大、频率不稳定或数值异常，控制器就无法正常工作。具体来说：

**位置控制器**需要当前的关节角度来判断是否到达目标。
**速度控制器**需要当前的关节速度来计算加速度指令。
**力矩控制器**需要当前的关节力矩来调整输出 torque。
**导纳/阻抗控制器**需要末端的力和位姿来调节刚度与阻尼参数。

控制器的性能上限取决于状态观测的质量。一个控制频率为 1kHz 的控制器，如果状态更新频率只有 100Hz，那它实际上有 90% 的控制周期在使用过期或插值得到的状态数据。

### 为日志系统提供复盘依据

机器人运行过程中产生的所有状态数据，都应被完整记录。这些记录的用途至少包括：

**故障复盘**：机器人撞了什么东西？是因为关节角度异常还是力矩超限？日志中的状态数据可以还原事发前后的完整机器人构型。
**数据集构建**：从真实机器人采集训练数据时，状态数据与传感器数据必须一一对应。关节角度、末端位姿、基座速度等字段是 imitation learning 和 offline RL 数据集的核心组成部分。
**仿真对齐**：将真机采集的状态数据回放到仿真器中，可以验证仿真模型是否准确、策略在仿真和真机上的行为是否一致。
**性能评估**：通过统计历史状态数据，可以评估任务成功率、执行时间分布、力矩消耗、关节温度变化等指标。

因此，状态观测不仅是"看一眼当前角度"这么简单。它需要回答一系列问题：数据从哪来、什么时候产生的、属于哪个坐标系、是否可信、如果不可信，错误码是什么。

## 状态分类：按对象划分

机器人系统中的状态信息种类繁多，如果不加分类地讨论，很容易陷入细节而失去整体视角。从工程接口的角度，可以按**被观测的对象**将状态划分为以下五类：

### 关节状态

关节状态描述机器人每个独立自由度的当前运动状态。这是机器人状态中最基础、更新频率最高的一类数据。典型字段包括关节名称、位置、速度、力矩，以及关节限位、温度、电流等辅助信息。关节状态的一个关键在于**关节名称和数组顺序的一致性**——如果状态数据中的关节顺序与控制命令中的关节顺序不一致，策略发出的命令就会被错误地路由到其他关节，这比数值噪声危险得多。

关节状态的详细字段定义和常见问题见"关节状态"子文档。

### 基座状态

基座状态描述机器人整体在空间中的位置和运动。对于固定基座的机械臂（如桌面上的 Franka），基座状态通常是静态的（固定在 world 或 base_link 下）；对于移动底盘（如 Stretch 的差速底座），基座状态是动态更新的（来自轮式里程计或 SLAM）；对于四足或人形机器人，基座状态是浮动基座（floating base），其六自由度位姿本身就是状态估计的输出。

基座状态的关键在于**区分基座类型**以及**明确状态的来源和质量**。同样的 `base_pose` 字段，来自 motion capture 的精度与来自轮式里程计的精度可能差一个数量级，下游使用前必须知道这个差异。基座状态的详细讨论见"底盘状态"子文档。

### 末端工具状态

末端工具状态描述机器人与环境交互的最终环节——夹爪、吸盘、灵巧手等末端执行器的当前状态。它与关节状态的核心区别在于：关节状态反映的是"机器人本体怎么动"，末端工具状态反映的是"操作有没有发生、有没有成功"。

例如，关节角度只能告诉策略夹爪的开合宽度，但无法直接告诉策略"物体是否已经被抓住"——这个信息需要来自末端的力反馈、接触检测或滑移检测。在抓取、吸附、按压、插入等接触密集型任务中，末端工具状态是判断任务成功与否的直接依据。详细内容见"末端工具状态"子文档。

### 传感器状态

传感器状态关注的不是传感器数据本身（图像、点云、IMU 读数等），而是**这路传感器数据是否可用、是否可信**。对于每一路传感器，至少需要记录其挂载坐标系、采样频率、分辨率、标定版本和健康状态。对于相机类传感器，内参和外参版本直接影响下游感知结果的正确性；对于 IMU 和力传感器，bias、量程、饱和状态直接影响数据质量。

传感器状态的作用类似于一个"数据质量网关"——在策略或算法使用传感器数据之前，先检查传感器是否在线、标定是否过期、数据是否断流。详细内容见"传感器状态"子文档。

### 系统与故障状态

除上述四类按对象划分的状态外，机器人系统还有一个贯穿所有子系统的状态维度：**系统级状态和故障状态**。这包括：

- **控制模式**：当前处于位置控制、速度控制还是力矩控制模式。
- **急停状态**：硬件急停是否被触发、软件急停是否激活。
- **通信状态**：各节点是否在线、通信延迟是否超阈值。
- **电源状态**：电池电量、电压、电流。
- **故障码**：具体的故障类型和故障代码，方便诊断。

系统与故障状态通常以独立的状态字或 flag 字段出现在各类状态消息中，而不是单独构成一类消息。但它在工程实践中的重要性不亚于任何一类物理状态——一个未记录的故障码可能让整个数据采集 session 作废，而开发者事后根本不知道发生了什么。

## 状态字段的通用要求

无论哪种类型的状态数据，每个字段都必须携带足够的元信息，使下游消费者（策略、控制器、日志模块、数据分析脚本）能够正确解析和使用这些数据。以下六类元信息是状态字段的共同要求：

### 数值与单位

状态字段的数值必须明确其物理单位。在机器人工程中，最常出问题的不是数值本身，而是单位不一致。典型的问题包括：角度用弧度还是度、线速度用 m/s 还是 mm/s、力矩用 N·m 还是 mN·m。不同厂商的 SDK、不同仿真平台、不同通信协议可能采用不同的单位约定。如果在数据采集、策略训练和真机部署三个阶段没有统一单位，就会出现数值看起来正确但物理含义完全错误的情况。

一个简单的规则：**所有状态字段在发布时必须附带单位信息，或在系统级配置中统一声明单位制**。对于 ROS 2 生态，消息定义中的注释应明确标注单位；对于自定义协议，应在文档中给出完整的单位表。

### 时间戳

每一个状态数据点都必须携带其**产生时刻**的时间戳，而非接收时刻或处理时刻。时间戳的作用至少有三：

**时间对齐**：不同传感器和状态源具有不同的采样频率和延迟，只有通过时间戳才能将它们对齐到同一时刻，构建策略的同步观测。
**延迟计算**：通过比较状态时间戳与当前时刻，可以估算状态数据的端到端延迟，判断是否仍在控制器的可用窗口内。
**日志回放**：回放时按时间戳排序和插值，才能忠实地还原运行时的状态序列。

时间戳必须是单调递增的（至少对同一状态源而言），如果出现时间戳回退或乱序，说明系统存在时钟同步问题，需要在软件接口层面解决。

### 坐标系归属

任何具有空间属性的状态（位姿、速度、力、加速度），都必须声明其参考坐标系，即 `frame_id`。例如，末端位姿是相对于 `base_link` 还是相对于 `world`？基座速度是在 `odom` 帧下还是 `base_link` 帧下？力矩是在关节坐标系下还是在末端工具坐标系下？

frame_id 不明确的状态数据，在下游使用时极易被错误地归入另一个坐标系，导致整个空间推理链出错。这一要求与第 3 节"空间关系与坐标约定"中建立的坐标树直接对应——每个 frame_id 必须是坐标树中存在且语义正确的节点。

### 数据来源

状态数据应标注其**来源**，即这个数据是直接测量得到的还是通过估计算法间接得到的。常见的来源标签包括：

**encoder**：来自关节编码器的直接读数。
**imu**：来自 IMU 的直接测量。
**state_estimator**：来自状态估计算法（如运动学正解、EKF、VIO）的间接输出。
**sim_ground_truth**：仿真器中直接获取的真实值（在真机上不可用）。
**mocap**：来自运动捕捉系统的外部测量。
**wheel_odometry**：来自轮式里程计的推算值。

标注来源的作用在于：当策略从仿真迁移到真机时，某些在仿真中可用的"真实值"来源在真机上不存在，必须替换为对应的估计值。如果来源字段缺失，这个替换过程将无法自动化。

### 有效性标记

并非每一条状态数据都是有效的。传感器可能断流，关节编码器可能故障，状态估计算法可能在某个时刻发散。因此，状态数据必须携带有效性标记（如 `data_valid`、`stale`、`timeout` flag），告诉下游消费者这条数据是否可以被信任。

有效性标记通常是一个布尔值或枚举类型。当标记为无效时，应同时给出错误码，说明无效的原因。下游策略收到无效状态时，应采取安全行为（如保持当前姿态或回安全位），而非继续使用无效数据做决策。

### 错误码

当状态数据异常时，错误码提供了**可操作的诊断信息**。错误码不应只是一串数字或模糊的"error"字符串，而应包含足够的语义信息让开发者快速定位问题。一个好的错误码体系至少应区分以下层次：

**硬件层**：编码器故障、电机过温、通信超时。
**软件层**：状态估计发散、数据频率不达标、时间戳异常。
**配置层**：标定文件缺失、坐标系未发布、参数版本不匹配。

错误码的详细设计属于具体系统的实现细节，但作为接口规范，必须要求每一类状态消息预留错误码字段，并在系统文档中给出错误码的语义表。

## 状态观测与状态估计的边界

在讨论机器人状态时，一个常见的混淆是：把状态观测的**接口格式**和状态估计的**算法实现**混为一谈。本章明确二者的边界：

**状态观测（本章范围）**关注的是：

状态数据的字段定义、类型、单位和语义。
状态数据的时序要求（频率、延迟、时间戳单调性）。
状态数据的坐标系归属和数据来源标注。
状态数据的质量检查（有效性、一致性、完整性）。
状态数据的记录格式和对下游策略/控制器的接口约定。

**状态估计（及后续专题范围）**关注的是：

如何从原始传感器数据估计出机器人的完整状态：例如通过扩展卡尔曼滤波融合轮式里程计和 IMU 得到基座位姿，通过视觉惯性里程计估计无人机位姿，通过全身运动学估计人形机器人的质心状态。
定位算法：SLAM、扫描匹配、全局重定位。
建图算法：占据栅格地图、点云地图、语义地图。
滤波与平滑：粒子滤波、图优化、因子图。

简单说：**本章定义"状态的接口长什么样"，状态估计算法回答"这些状态值怎么算出来的"**。这个分工的意义在于：策略和控制器不需要知道状态值是通过 EKF 还是 VIO 算出来的，它们只需要知道状态字段的格式、单位、坐标系和是否可信。同样，状态估计算法的开发者也不需要关心策略如何使用这些状态，只需要按约定格式输出即可。

但在工程实践中，有一个接口层面必须注意的问题：**状态估计的输出往往带有不确定性（covariance / confidence）**，这个不确定性本身就是状态字段的一部分。例如，一个 VIO 输出的基座位姿，如果相机视野中特征点稀少，其协方差矩阵会显著增大。策略如果只使用位姿值而忽略协方差，可能会在状态不可靠时做出过于激进的决策。因此，状态 schema 中应预留 covariance 或 confidence 字段，供状态估计算法输出。

## 最小状态 Schema

综合以上讨论，本节给出一个作者应覆盖的最小状态 schema。这个 schema 的目的是为后续各章节（数据集制作、策略训练、真机部署、仿真对齐）提供一个统一的字段参考，避免每个章节各自重新定义状态格式。

以下 schema 按消息类型组织，每类消息包含必要字段和推荐字段。必要字段是任何机器人系统都应提供的基础信息；推荐字段在工程实践中能显著提升数据质量和调试效率，视具体平台的支持程度决定是否包含。

### JointState

必要字段：

| 字段 | 类型 | 单位 | 说明 |
|------|------|------|------|
| `joint_names` | `string[]` | — | 关节名称列表，顺序与数据数组一致，名称应与模型文件中的 joint name 严格匹配 |
| `position` | `float64[]` | rad（旋转关节）或 m（平移关节） | 当前关节位置，长度和顺序与 `joint_names` 一致 |
| `velocity` | `float64[]` | rad/s 或 m/s | 当前关节速度 |
| `effort` | `float64[]` | N·m 或 N | 当前关节力矩/力 |
| `timestamp` | `uint64` | ns 或 μs（系统统一） | 数据产生时刻的时间戳 |

推荐字段：

| 字段 | 类型 | 单位 | 说明 |
|------|------|------|------|
| `position_limit_lower` | `float64[]` | 同 position | 关节位置下限 |
| `position_limit_upper` | `float64[]` | 同 position | 关节位置上限 |
| `velocity_limit` | `float64[]` | 同 velocity | 关节速度上限 |
| `effort_limit` | `float64[]` | 同 effort | 关节力矩上限 |
| `temperature` | `float64[]` | ℃ | 关节电机温度 |
| `current` | `float64[]` | A | 关节电机电流 |
| `control_mode` | `uint8[]` | — | 每个关节当前的控制模式（位置/速度/力矩/空闲/故障） |
| `fault` | `uint8[]` | — | 每个关节的故障码，0 表示正常 |
| `data_valid` | `bool` | — | 本条状态数据是否有效 |

### BaseState

必要字段：

| 字段 | 类型 | 单位 | 说明 |
|------|------|------|------|
| `frame_id` | `string` | — | 位姿和速度的参考坐标系 |
| `child_frame_id` | `string` | — | 被描述的坐标系（通常是 `base_link`） |
| `pose` | `Pose` | m, 四元数 | 基座在参考坐标系下的六自由度位姿 |
| `twist` | `Twist` | m/s, rad/s | 基座的线速度和角速度 |
| `timestamp` | `uint64` | ns 或 μs | 数据产生时刻的时间戳 |

推荐字段：

| 字段 | 类型 | 单位 | 说明 |
|------|------|------|------|
| `source` | `string` | — | 数据来源（`wheel_odometry` / `imu` / `vio` / `mocap` / `sim_ground_truth`） |
| `pose_covariance` | `float64[36]` | — | 位姿的 6×6 协方差矩阵（行主序） |
| `twist_covariance` | `float64[36]` | — | 速度的 6×6 协方差矩阵 |
| `tracking_status` | `uint8` | — | 定位跟踪状态（正常/降级/丢失/未初始化） |
| `reset_flag` | `bool` | — | 状态估计是否发生复位（如里程计漂移纠正后的跳变） |

### EndEffectorState

必要字段：

| 字段 | 类型 | 单位 | 说明 |
|------|------|------|------|
| `name` | `string` | — | 末端工具名称，与模型文件中的命名一致 |
| `frame_id` | `string` | — | 末端工具位姿的参考坐标系 |
| `pose` | `Pose` | m, 四元数 | 末端工具在参考坐标系下的位姿 |
| `timestamp` | `uint64` | ns 或 μs | 数据产生时刻的时间戳 |

推荐字段（按末端工具类型二选一或组合）：

对于夹爪类：

| 字段 | 类型 | 单位 | 说明 |
|------|------|------|------|
| `gripper_width` | `float64` | m | 夹爪当前开合宽度 |
| `gripper_force` | `float64` | N | 夹爪当前夹持力 |
| `gripper_velocity` | `float64` | m/s | 夹爪当前开合速度 |
| `object_held` | `bool` | — | 是否检测到物体被抓持 |
| `contact_detected` | `bool[]` | — | 各指是否检测到接触 |
| `slip_detected` | `bool` | — | 是否检测到物体滑动 |

对于吸盘类：

| 字段 | 类型 | 单位 | 说明 |
|------|------|------|------|
| `vacuum_pressure` | `float64` | kPa 或 bar | 当前真空压力 |
| `object_attached` | `bool` | — | 是否检测到物体被吸附 |

### Schema 使用说明

上述 schema 的设计遵循以下原则：

**独立于具体平台**：所有字段均以通用术语定义，不绑定 ROS 2、LCM、protobuf 或任何具体通信框架。在实际系统中，将这些字段映射到对应的消息定义即可。
**可裁剪**：推荐字段根据实际平台的支持程度决定是否启用。但必要字段在任何部署场景下都不应缺失，否则会严重影响后续环节（数据集构建、策略训练、日志复盘）的可用性。
**可扩展**：不同机器人平台可能有特殊的硬件传感器或控制模式，可以在上述 schema 基础上追加平台特有字段，但不应修改现有字段的语义。
**与模型文件对齐**：所有命名（joint name、frame_id、sensor name、end-effector name）必须与模型文件中定义的名称严格一致，否则数据采集和处理流程中会出现字段无法对应的错误。

在后续章节中，"数据集制作"可以直接引用此 schema 定义数据格式，"策略训练"可以基于此 schema 定义 observation space，"真机部署"可以基于此 schema 验证状态字段是否完整。

## 状态质量的核心维度

定义了状态的格式和字段之后，还需要回答一个问题：数据来了，但它**好不好**？状态质量直接影响策略训练的效果和真机部署的可靠性。从工程角度，可以从以下几个维度评估状态质量：

### 频率

每种状态数据都应有预期的发布频率。关节状态通常需要 100-1000Hz（取决于控制回路要求），基座状态通常需要 50-200Hz，传感器状态通常与传感器本身的采样率一致。频率不达标意味着控制器在部分周期内没有新鲜的状态数据可用，只能使用旧值或插值，这会降低控制精度甚至导致不稳定。

### 延迟

延迟是指从状态在物理世界产生到被策略或控制器接收之间的时间差。延迟的来源包括传感器采样时间、通信传输时间、序列化和反序列化时间、以及中间节点的处理时间。过高的延迟会让策略基于"过去"的状态做决策，在动态任务中尤为危险——机器人已经在新的位置了，策略还在根据旧位置计算动作。

### 抖动

抖动是指相邻两次状态更新的时间间隔的不稳定性。即使平均频率达标，如果时间间隔忽大忽小（例如有的周期 8ms、有的周期 12ms），控制器的时序也会受到干扰。抖动严重时，控制器可能出现周期性的超调和振荡。

### 丢帧

丢帧是指在预期的时间窗口内没有收到新的状态数据。丢帧可能是由于网络拥塞、节点负载过高或传感器硬件故障导致。持续的丢帧会在状态序列中产生空洞，影响日志回放的数据完整性和离线训练的数据质量。

### 时间戳单调性

同一状态源的时间戳必须是单调递增的。时间戳回退（后一条数据的时间戳早于前一条）通常意味着系统时钟发生了调整（如 NTP 同步）或数据缓冲区的出队顺序出错。时间戳乱序会破坏策略的时序推理和日志的按序回放。

### 单位一致性

同一字段在不同状态源、不同平台、不同版本之间必须使用相同的单位。一个典型的事故模式是：仿真器中使用弧度，真机 SDK 使用度，而策略训练数据中混用了两种单位。这不是算法问题，但在工程中却极为常见且难以排查。

### 坐标系一致性

所有带空间属性的状态字段，其 `frame_id` 必须与坐标树中发布的变换一致。如果状态声称在 `camera_color_frame` 下，但坐标树中没有从 `base_link` 到 `camera_color_frame` 的变换，这条状态数据就无法被正确定位。

这些维度的具体检查方法和处理策略在"状态质量与数据一致性"子文档中详细展开。

## 本章小结

机器人状态观测是具身智能系统中连接"机器人是什么"和"机器人怎么动"的桥梁。本章从工程接口的角度，将状态观测分解为五个按对象划分的类别——关节状态、基座状态、末端工具状态、传感器状态、系统故障状态——并定义了每一类状态的字段要求和元信息规范。

状态数据的质量不仅取决于数值精度，更取决于其携带的元信息是否完整：数值和单位、时间戳、坐标系归属、数据来源、有效性标记和错误码，这六项元信息是任何状态字段都不可或缺的。缺少任何一项，都会在下游环节（策略训练、控制器执行、日志复盘）中引发难以排查的问题。

本章明确区分了状态观测的接口层面和状态估计的算法层面：前者关注"状态字段长什么样"，后者关注"状态值怎么算出来"。这个分工让策略和控制器的开发者只需关心接口约定，而状态估计算法的开发者只需按约定格式输出，双方通过一个共同的状态 schema 协同工作。

最后，本章给出了一个最小但完整的状态 schema，包含 JointState、BaseState、EndEffectorState、SensorState 和 SystemFaultState 五类消息的字段定义。这个 schema 将作为后续所有章节的共同参考——数据集构建、策略训练、真机部署、仿真对齐，都以这套字段定义为基准。每类状态的具体字段语义、使用场景和常见问题，在各子文档中进一步展开。
