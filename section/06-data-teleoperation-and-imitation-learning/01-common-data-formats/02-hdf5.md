# HDF5

目标：理解 HDF5 在机器人示教数据中的层次化组织方式，能审计 observation、action、next_obs、图像和 split 的语义是否可靠。

HDF5 是机器人学习里非常常见的一类数据容器。很多仿真基准、旧版机器人数据集和 imitation learning 项目，都会把一批 demonstration（示教轨迹）保存成一个 `.hdf5` 文件。它不像普通图片文件夹那样“一张图一个文件”，也不像 CSV 那样只适合二维表格，而是可以在一个二进制文件里组织多层 group、数组、字符串和属性信息。

学习 HDF5 不是为了背它的 API，而是为了回答三个实际问题：

1. 一个 HDF5 机器人数据集里面通常放了什么。
2. 为什么它很适合保存仿真轨迹和旧 benchmark，但也容易变成“黑盒大包”。
3. 如果以后要把 HDF5 转成 LeRobot、RLDS 或其它格式，哪些语义最容易丢。

本节只讲 HDF5 作为机器人数据容器的使用方式，不展开 HDF5 底层存储实现。

## 为什么机器人数据常用层次化容器

机器人数据和普通图像分类数据最大的区别是：它不是一张图对应一个标签，而是一段连续交互过程。

以一个简单的桌面抓取任务为例，一条 episode 可能包含：

```text
episode_000
  frame 0: 图像 + 机器人状态 + action + timestamp
  frame 1: 图像 + 机器人状态 + action + timestamp
  frame 2: 图像 + 机器人状态 + action + timestamp
  ...
  task: "pick up the block"
  success: true / false
```

如果采集频率是 30 FPS，一条 episode 长 60 秒，那么单相机就有：

```text
60 seconds × 30 fps = 1800 frames
```

如果有两个相机，就是：

```text
2 cameras × 1800 frames = 3600 images
```

这还没有算关节位置、末端位姿、夹爪状态、动作、奖励、done 标志、任务文本和环境 metadata。

如果把每一帧都存成一张单独的 PNG，再给每条轨迹配一堆 JSON 文件，很快就会产生几十万甚至几百万个小文件。这对训练、拷贝、上传、版本管理和远程读取都不友好。

因此，机器人数据通常会做两件事：

```text
低维连续数据  ->  放进数组或列式容器，例如 HDF5、Parquet、Zarr
连续图像序列  ->  压成视频，例如 MP4、H.264、AV1
```

HDF5 的吸引力就在这里：它可以把一批 episode 的数组、图像、状态、动作和环境信息放进一个层次化文件里，像一个可切片读取的大型实验记录包。

需要注意，HDF5 本身不是“自动压缩格式”。它支持对 dataset 使用 chunking、gzip、lzf 等压缩或分块配置，但是否压缩、如何分块、读取是否高效，都取决于具体写入方式。因此读 HDF5 时除了看 key 和 shape，也要留意数据是否做了压缩、chunk size 是否适合当前访问模式。

但也要先记住一句话：

> HDF5 让数据更容易打包，不等于让数据语义更清楚。

实际使用 HDF5 时，最难的不是“能不能打开文件”，而是“能不能理解每个 key 的含义、每个数组的维度、每个动作和观测的时间关系”。

## HDF5 到底是什么

HDF5 的全称是 **Hierarchical Data Format version 5**，可以理解为“层次化二进制数据容器”。

它的结构很像一个压缩在单个文件里的文件系统：

```text
dataset.hdf5
  group_a/
    dataset_1
    dataset_2
  group_b/
    subgroup/
      dataset_3
  attrs:
    some_metadata
```

里面有三个基础概念。

### group：像文件夹

`group` 可以理解成文件夹，用来组织层级。例如：

```text
data/
  demo_0/
  demo_1/
```

这里的 `data`、`demo_0`、`demo_1` 都可以是 group。

### dataset：像数组文件

`dataset` 是真正存数组的地方。例如：

```text
actions
robot0_joint_pos
agentview_image
```

它们可以是二维数组、三维数组、四维数组，也可以是字符串数组或压缩后的字节序列。

比如：

```text
actions: shape = [T, 7]
agentview_image: shape = [T, H, W, 3]
```

其中 `T` 是时间步数量。

### attrs：像附在对象上的说明

`attrs` 是属性，可以挂在整个文件、某个 group 或某个 dataset 上，用来保存补充信息。例如：

```text
env_args
total_samples
robot_name
camera_config
```

在机器人仿真数据里，`env_args` 很常见，它可能记录环境名称、任务配置、仿真资产和控制参数。

一个最小的 HDF5 读取脚本通常会先打印整棵树：

```python
import h5py

path = "dataset.hdf5"

with h5py.File(path, "r") as f:
    def walk(name, obj):
        if hasattr(obj, "shape"):
            print(name, obj.shape, obj.dtype)
        else:
            print(name)
    f.visititems(walk)

    print("file attrs:", dict(f.attrs))
```

初学者接手一个 HDF5 数据集时，第一件事不是训练模型，而是先跑类似脚本，把 group/key 树、shape、dtype 和 attrs 打印出来。

## 机器人 HDF5 常见结构

许多机器人数据集，尤其是 robomimic、robosuite 以及一些仿真 benchmark，常见结构接近下面这样：

```text
dataset.hdf5
  data/
    demo_0/
      actions
      rewards
      dones
      obs/
        agentview_image
        robot0_eye_in_hand_image
        robot0_joint_pos
        robot0_eef_pos
        robot0_gripper_qpos
      next_obs/
        agentview_image
        robot0_eye_in_hand_image
        robot0_joint_pos
        robot0_eef_pos
        robot0_gripper_qpos
    demo_1/
      ...
  mask/
    train
    valid
  attrs:
    env_args
    total_samples
```

这棵树可以分成几层来看。

### `data/demo_i`：一条示教轨迹

`demo_0`、`demo_1` 通常各自表示一条 demonstration，也就是一条 episode。它们是训练和切分的基本单位。

这点很重要：做 train/val/test 切分时，应该按 demo 或 episode 切，而不是按 frame 随机切。因为同一条 demo 中相邻帧高度相似，按 frame 切会造成数据泄漏。

### `obs`：动作执行前的观测

`obs` 保存当前时间步的观测。例如：

```text
obs/agentview_image
obs/robot0_joint_pos
obs/robot0_eef_pos
obs/robot0_gripper_qpos
```

这些字段可以被策略作为输入。

### `actions`：当前时间步要执行的动作

`actions` 通常是一个形状为 `[T, action_dim]` 的数组，例如：

```text
actions: [T, 7]
```

但 `[T, 7]` 只说明它有 7 维，不说明它是什么动作。它可能是：

```text
末端位姿增量: [dx, dy, dz, droll, dpitch, dyaw, gripper]
```

也可能是：

```text
关节位置: [joint1, joint2, ..., joint7]
```

还可能是归一化后的控制命令。只看 shape 不能判断语义，必须结合文档、代码或 attrs。

### `next_obs`：动作执行后的观测

`next_obs` 保存执行当前 action 之后得到的下一帧观测。

它和 `obs` 的时间关系是：

```text
obs_t  -- action_t -->  next_obs_t = obs_{t+1}
```

这对强化学习很有用，因为 RL 经常需要 `(s_t, a_t, r_t, s_{t+1}, done_t)`。

但对行为克隆（Behavior Cloning, BC）来说，最常见的监督关系是：

```text
obs_t -> action_t
```

也就是说，训练策略时通常用当前 `obs` 预测当前 `action`，不要误把 `next_obs` 当成当前输入。

### `rewards` 和 `dones`：强化学习和回放相关

`rewards` 表示每一步奖励，`dones` 表示 episode 是否结束。在仿真环境中，它们经常由环境自动生成。

但是在模仿学习里，`rewards` 不一定参与训练。很多 BC 任务只需要：

```text
observation -> action
```

这时 `rewards` 和 `dones` 更像辅助 metadata，用于过滤、回放或评估。

### `mask/train` 和 `mask/valid`：切分信息

一些 HDF5 数据集会在 `mask/` 里保存 train/valid 划分。例如：

```text
mask/
  train
  valid
```

这提醒我们：split 不是训练脚本临时决定的小事，它本身也是数据格式的一部分。

如果转换到 LeRobot 或其它格式，不能只转 `data/demo_*`，也要考虑原来的 split 是否保留。

## obs、next_obs 和 action 的时间关系

很多 HDF5 转换错误都出在时间关系上，所以这里单独讲。

一条轨迹可以写成：

```text
t = 0:  obs_0  -> action_0 -> obs_1
t = 1:  obs_1  -> action_1 -> obs_2
t = 2:  obs_2  -> action_2 -> obs_3
...
```

如果 HDF5 同时保存 `obs` 和 `next_obs`，那么通常有：

```text
obs[t]      = obs_t
actions[t]  = action_t
next_obs[t] = obs_{t+1}
```

因此，用于 BC 训练时，常见样本应该是：

```text
input:  obs[t]
target: actions[t]
```

不是：

```text
input:  next_obs[t]
target: actions[t]
```

后者会变成“用动作执行后的画面预测动作”，时间方向错了。

一个简化图：

```text
正确的 BC 对齐：

frame t
  obs[t] ------------------> actions[t]
    |
    | 执行动作后
    v
  next_obs[t]

错误用法：

next_obs[t] --------------> actions[t]
```

这种错误很隐蔽，因为数组长度通常仍然一致，训练脚本不会报错，但模型学到的是错误的因果关系。

如果最后一帧没有有效 action，也要小心。某些格式会保存 terminal observation，但没有下一步动作；这种帧不能直接当作普通监督样本。

## 图像在 HDF5 里怎么存

HDF5 可以保存图像，但不同项目做法不一样。常见有三种。

### 方式一：原始图像数组

例如：

```text
obs/agentview_image: [T, H, W, 3], uint8
```

优点是读取后就是图像数组，语义直接。如果 dataset 写入时启用了 chunking 或压缩，还可以在一定程度上减少磁盘占用。

缺点是体积仍然可能很大，而且压缩和分块配置会影响随机读取效率。假设：

```text
T = 1800
H = 480
W = 640
C = 3
```

单相机一条 episode 的原始 RGB 大小大约是：

```text
1800 × 480 × 640 × 3 bytes ≈ 1.66 GB
```

这还没有算多个相机和其它字段。

### 方式二：JPEG / PNG bytes

有些数据会把每帧图像编码成 JPEG 或 PNG bytes，再存到 HDF5 里。

优点是体积小很多。

缺点是读取时需要额外解码，而且你必须知道：

```text
这是 JPEG 还是 PNG？
通道顺序是 RGB 还是 BGR？
是否做过 resize？
是否有压缩伪影？
```

### 方式三：图像不放 HDF5，只在 HDF5 里存索引

也有项目把视频或图像单独放在外部文件里，HDF5 只保存路径或索引。

这种做法更接近现代数据湖思路，但要求跨文件同步非常严谨。

```text
dataset.hdf5
  demo_0/
    actions
    timestamps
    image_paths

videos/
  demo_0_front.mp4
  demo_0_wrist.mp4
```

这时审计重点变成：HDF5 里的第 t 行，是否真的对应视频里的第 t 帧。

## HDF5 的优点和代价

HDF5 的优点很明显。

### 优点一：集中打包

一个文件里可以放很多 episode，方便传输和归档。

```text
one dataset.hdf5
  -> many demos
  -> many arrays
  -> metadata attrs
```

这对仿真 benchmark 很舒服，因为环境状态、动作、奖励和 done 都可以在一个文件里保存。

### 优点二：层次结构自然

HDF5 的 group/dataset 结构很适合表达：

```text
data/demo_0/obs/image
data/demo_0/actions
data/demo_1/obs/image
data/demo_1/actions
```

比一堆散乱的 `.npy` 文件更清楚。

### 优点三：数组切片方便

HDF5 支持按数组切片读取。例如只读某一条 demo、某个字段或某个时间段。这对大数组很有用。

### 优点四：旧生态支持多

robomimic、robosuite 以及许多旧版 imitation learning 项目都使用 HDF5。学会读 HDF5，能帮助你接手很多已有数据。

但它的代价同样明显。

### 代价一：容易变成黑盒大包

HDF5 能存很多东西，但不强制你写清语义。所以有些文件里只有：

```text
actions: shape [T, 7]
states: shape [T, 32]
```

但没有说明每一维是什么。

这时文件能打开，不代表能正确训练。

### 代价二：Web / Hub 预览不友好

现代数据平台更容易预览 Parquet、JSON、MP4 这类格式。HDF5 在网页上通常不容易直接查看内部结构，更像一个需要专门工具打开的大包。

### 代价三：大文件损坏影响范围大

如果所有数据都在一个巨大 HDF5 文件里，文件损坏会影响很多 episode。分片可以缓解，但又需要额外管理。

### 代价四：并发写入和远程读取不一定舒服

HDF5 很适合本地单机读取，但在云端对象存储、Hub streaming、分布式训练和并发写入场景下，不一定比 Parquet / MP4 / Zarr 更自然。

## HDF5 和 Parquet + MP4 的差别

LeRobot v3 更偏向 Parquet + MP4 的组合，而不是把所有东西放进一个 HDF5。这不是因为 HDF5 “不好”，而是两者的工程目标不同。

| 对比项 | HDF5 | Parquet + MP4 |
|---|---|---|
| 组织方式 | 一个或少量层次化大文件 | 低维表格、视频、metadata 分层存放 |
| 低维数据 | 数组 dataset | Parquet 列式表格 |
| 图像数据 | 原始数组或压缩 bytes | MP4 视频 |
| episode 边界 | 常在 group 名或内部字段里 | 显式写在 metadata 中 |
| 人工检查 | 需要 h5py / HDFView 等工具 | 表格和视频更容易单独检查 |
| 远程托管 | 不如表格/视频友好 | 更适合 Hub 和 streaming |
| 典型场景 | 仿真 benchmark、旧数据集 | 大规模训练、共享、版本化 |

可以这样理解：

```text
HDF5:
  把很多东西装进一个大盒子

Parquet + MP4:
  低维数据、视频、metadata 分开管理
```

HDF5 更像“归档容器”，Parquet + MP4 更像“工程化数据目录”。

在小规模仿真、算法对比和旧代码复现中，HDF5 仍然很合适；在大规模数据共享、远程读取和长期维护中，LeRobot v3 这种分层组织会更舒服。

## Zarr 和 ReplayBuffer

除了 HDF5 和 Parquet，机器人学习里还经常见到 Zarr，尤其是在 Diffusion Policy 相关项目中。

Zarr 是一种面向大数组的分块存储格式。它适合把多条 episode 的数据沿时间维拼成一个大的 replay buffer，然后训练时从里面随机切固定长度窗口。

可以想象成：

```text
episode_0: frames 0 ~ 99
episode_1: frames 100 ~ 249
episode_2: frames 250 ~ 400

拼成一个大时间轴：
global_frame 0, 1, 2, ..., 400
```

训练时采样窗口：

```text
window A: global_frame 20 ~ 35
window B: global_frame 180 ~ 195
window C: global_frame 300 ~ 315
```

这种方式对扩散策略很方便，因为模型经常要学习一段 action chunk，而不是单步 action。

真实项目里通常还会保存类似 `episode_ends`、`episode_starts` 或 `episode_index` 的边界索引，告诉采样器每条 episode 在这个大时间轴中的起止位置。

但 Zarr 的风险是：

```text
episode 边界必须额外保存，并且采样窗口不能跨过边界；
字段语义通常依赖项目代码；
转换到 LeRobot 时，需要恢复 episode/frame 索引；
如果窗口跨 episode 边界，训练样本会出错。
```

所以 Zarr 很适合训练时的数据读取，但不一定适合作为唯一的公开数据说明格式。

## 从 HDF5 转 LeRobot

从 HDF5 转 LeRobot 时，不能只做字段重命名。一个比较完整的流程是：

```text
打开 HDF5
  -> 打印 group/key 树、shape、dtype、attrs
  -> 逐条读取 demo
  -> 确认 obs/action/next_obs 时间关系
  -> 映射 feature 名称和维度语义
  -> 写低维数据到 Parquet
  -> 写图像或视频到 MP4
  -> 写 meta/info.json
  -> 写 meta/tasks
  -> 写 meta/episodes
  -> 计算 meta/stats.json
  -> 抽样可视化和回放
```

其中最容易出错的是下面几类。

### 1. action 对齐

如果源文件有 `obs` 和 `next_obs`，不要错用 `next_obs` 作为 BC 输入。

检查方式：

```text
随机抽一条 demo
查看 obs[t]、action[t]、next_obs[t]
确认 action[t] 是从 obs[t] 开始执行的动作
```

### 2. gripper 语义

夹爪字段经常不统一。可能有：

```text
0 = 张开，1 = 闭合
1 = 张开，0 = 闭合
连续宽度，单位米
归一化命令，范围 [-1, 1]
```

如果 gripper 语义错了，模型会学到相反的开合动作。

### 3. state/action 维度名

不能只写：

```text
action: shape [7]
```

必须写清楚：

```text
action[0] = dx
action[1] = dy
action[2] = dz
action[3] = droll
action[4] = dpitch
action[5] = dyaw
action[6] = gripper
```

或者如果是关节空间，也要写清每个 joint 的名称和单位。

### 4. 图像通道顺序

很多 Python 图像库默认 RGB，但 OpenCV 常用 BGR。HDF5 里的图像字段未必直接告诉你通道顺序。

如果 RGB/BGR 反了，训练脚本通常不会报错，但视觉模型看到的颜色分布会变。

### 5. FPS 和 timestamp

不要盲目写：

```text
fps = 30
```

要先看源数据是否有 timestamp。真实采集可能存在掉帧、抖动和不稳定间隔。

如果没有 timestamp，至少要在数据卡里说明 FPS 是来自采集配置、估计值还是硬编码假设。

### 6. success / done / terminal

`done=True` 不一定等于任务成功。它也可能表示：

```text
episode 到达最大步数；
环境被截断；
任务失败但结束；
仿真 reset。
```

如果你把所有 done 都当 success，训练集过滤就会错。

### 7. split

如果源 HDF5 已经有 `mask/train` 和 `mask/valid`，转换后要明确是否保留。

如果重新切分，应该按 episode、任务、场景或物体实例切，而不是按 frame 随机切。

## 一个最小审计脚本

下面是一个概念性脚本，说明接手 HDF5 数据集时可以先检查什么。

```python
import h5py
import numpy as np

def print_tree(path):
    with h5py.File(path, "r") as f:
        def walk(name, obj):
            if hasattr(obj, "shape"):
                print(f"{name}: shape={obj.shape}, dtype={obj.dtype}")
            else:
                print(name)
        f.visititems(walk)
        print("attrs:", dict(f.attrs))

def audit_demo(demo, fps=None):
    errors = []

    actions = demo["actions"]
    T = len(actions)

    if "obs" not in demo:
        errors.append("missing obs group")

    if "obs" in demo:
        for key in demo["obs"].keys():
            obs_len = len(demo["obs"][key])
            if obs_len != T:
                errors.append(f"obs/{key} length {obs_len} != actions length {T}")

    if "next_obs" in demo:
        for key in demo["next_obs"].keys():
            next_len = len(demo["next_obs"][key])
            if next_len != T:
                errors.append(f"next_obs/{key} length {next_len} != actions length {T}")

    if "timestamps" in demo:
        timestamps = np.asarray(demo["timestamps"])
        if len(timestamps) != T:
            errors.append("timestamp length mismatch")
        if np.any(np.diff(timestamps) <= 0):
            errors.append("timestamps are not strictly increasing")
        if fps is not None and len(timestamps) > 1:
            expected_dt = 1.0 / fps
            jitter = np.max(np.abs(np.diff(timestamps) - expected_dt))
            if jitter > expected_dt:
                errors.append("large timestamp jitter")

    if not np.isfinite(np.asarray(actions)).all():
        errors.append("actions contain NaN or Inf")

    return errors
```

这个脚本还不完整，但能帮你建立审计意识。真实项目还要继续检查：

```text
图像能否解码；
图像通道是否正确；
action 范围是否合理；
gripper 是否反向；
task 文本是否存在；
success 标签是否可信；
video / image frame 是否和 low-dimensional data 对齐。
```

## 一个转换设计例子

假设你有一个 robomimic 风格的 HDF5，结构如下：

```text
data/demo_0/
  obs/
    agentview_image
    robot0_eye_in_hand_image
    robot0_eef_pos
    robot0_gripper_qpos
  actions
  dones
```

你想转成 LeRobot，可以设计成：

| 源字段 | 目标 LeRobot feature | 说明 |
|---|---|---|
| `obs/agentview_image` | `observation.images.front` | 前视角图像，需确认 RGB/BGR 和分辨率 |
| `obs/robot0_eye_in_hand_image` | `observation.images.wrist` | 腕部相机，需确认是否与 action 同步 |
| `obs/robot0_eef_pos` | `observation.state` 的一部分 | 末端位置，写清单位 |
| `obs/robot0_gripper_qpos` | `observation.state` 的一部分 | 夹爪开度，写清范围 |
| `actions` | `action` | 写清 action space 和每一维含义 |
| `dones` | `is_last` 或 episode metadata | 不能默认等于 success |

同时，转换报告里至少要写：

```yaml
source:
  format: hdf5
  structure: robomimic-like
  demos_before: 1000

target:
  format: lerobot_v3
  image_features:
    - observation.images.front
    - observation.images.wrist
  state_features:
    - observation.state
  action_space: end_effector_delta_pose_plus_gripper

conversion_checks:
  obs_action_aligned: true
  rgb_bgr_checked: true
  gripper_semantics_checked: true
  episode_level_split: true
  stats_recomputed: true
```

这份报告的作用不是形式主义，而是让后面训练、复现、排错时知道这批数据从哪里来、怎么转过、哪些假设已经检查过。

## 常见易错点

### 1. 只看 shape，不看语义

`actions.shape = [T, 7]` 不能说明动作是什么。必须查每一维的含义、单位和范围。

### 2. 把 `next_obs` 当成当前观测

对 BC 来说，通常应该用 `obs[t] -> action[t]`，不是 `next_obs[t] -> action[t]`。

### 3. 把 `done` 当成 success

`done` 只表示 episode 结束，不一定表示任务成功。

### 4. 按 frame 切分 train/val/test

相邻帧高度相关，按 frame 切会造成数据泄漏。应按 episode 或更高层语义切。

### 5. 忘记保留环境 metadata

仿真数据里的 `env_args`、任务参数、资产版本非常重要。丢了这些，后面很难回放或复现。

### 6. 图像压缩后不检查

如果把 HDF5 图像数组转成 MP4，必须抽样检查是否花屏、掉帧、颜色反转或帧数不一致。

### 7. 合并多个 HDF5 后不重算统计量

只要删除、合并、改字段或改 split，就应该重新计算 stats。

## 小结

HDF5 是机器人学习里很重要的经典数据容器。它适合把仿真轨迹、示教数据和多层数组打包到一个文件里，也因此常见于 robomimic、robosuite 以及许多旧版 benchmark。

但使用 HDF5 时，困难通常不在读取文件，而在读懂文件。你需要知道每个 key 的含义、每个数组的维度、`obs` 和 `next_obs` 的时间关系、`action` 的单位和控制语义、图像通道和压缩方式，以及 split 和 metadata 是否保留。

可以把本节的核心压缩成一句话：

> HDF5 解决的是“把复杂轨迹装进一个容器”的问题，但不自动解决“这些轨迹语义是否清楚、时间是否对齐、能否安全训练”的问题。
