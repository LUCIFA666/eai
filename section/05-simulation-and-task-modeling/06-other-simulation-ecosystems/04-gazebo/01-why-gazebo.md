# 为什么机器人需要 Gazebo 仿真

目标：理解 Gazebo 解决的不是“有没有一个漂亮的 3D 场景”，而是机器人系统在上真机前如何低成本、可重复地联调。

真实机器人调试很贵。这里的“贵”不只是买机器人贵，还包括调试时间贵、场地贵、故障排查贵、摔机和撞人的风险也贵。一个移动机器人如果连 `/cmd_vel`、里程计、激光雷达、TF 坐标树和导航栈都没有理顺，就直接放到真实走廊里跑，问题会很难定位：到底是模型错了，控制错了，传感器错了，还是导航参数错了？

Gazebo 的价值在于先把这些问题放进一个可控环境里。你可以先在仿真世界里加载机器人模型，给它加上轮子、关节、碰撞体、惯量、激光雷达和 IMU，再让 ROS 2 节点像连接真机一样连接这些话题。等仿真里至少能稳定跑通，再把同一套 ROS 逻辑迁移到真机上，排查范围会小很多。

## 它主要帮我们做什么

| 需求 | 在真机上直接做的问题 | Gazebo 中的做法 |
|---|---|---|
| 系统联调 | 每次失败都可能撞车、卡住或损坏硬件 | 先在仿真里检查 topic、TF、控制链路 |
| 传感器验证 | 真实传感器受光照、遮挡、线缆和驱动影响 | 先用可控的 lidar、camera、IMU 输出验证算法 |
| 导航测试 | 地图、障碍物和人流不可控 | 固定 world，重复测试同一个场景 |
| 参数调试 | 调一次参数就要重新摆场地 | 在仿真里快速改参数、重启、记录结果 |
| 教学和复现 | 不是每个读者都有同一台机器人 | 用同一份模型和 world 复现实验流程 |

这里尤其要注意“系统联调”四个字。Gazebo 不是为了证明一个算法在真实世界一定可用，而是为了在上真机之前发现明显的问题。例如：机器人模型的轮距写错了，仿真里转弯半径就会不对；`/scan` 没有 bridge 到 ROS，导航栈就拿不到激光；TF 中 `base_link` 和 `laser` 关系错了，避障就会表现异常。这些问题在真机上也会出现，但在 Gazebo 里更容易复现和定位。

## Gazebo 适合什么，不适合什么

Gazebo 很适合做 ROS 机器人系统实验，尤其是移动机器人、导航、传感器话题、插件控制、仿真到真机的接口联调。它也能做机械臂和多机器人实验，但如果你的核心目标是极高吞吐的强化学习、照片级渲染、精密接触动力学优化，或者大规模室内任务基准，可能要同时考虑 Isaac Sim / Isaac Lab、MuJoCo、ManiSkill、Habitat 或 Drake。

所以读 Gazebo 时不要只问“它能不能仿真”。更应该问：我的 ROS 节点能不能像连接真机一样连接它？我的传感器话题、坐标系、控制命令和日志能不能在这里先闭环？如果答案是肯定的，Gazebo 就有很强的工程价值。

## 一个最小闭环

可以把 Gazebo 实验想成下面这个闭环：

```text
world + robot model
  -> Gazebo 运行物理和传感器
  -> 发布 /scan、/odom、/clock 等仿真数据
  -> ROS 2 节点读取数据并输出 /cmd_vel
  -> Gazebo 中的插件接收命令，让机器人运动
  -> 新的传感器数据继续反馈给 ROS 2
```

这个闭环跑通以后，再继续谈导航、避障、SLAM、机械臂控制或者多机器人协同才比较稳。如果闭环本身没跑通，后面的算法效果讨论大多没有意义。
