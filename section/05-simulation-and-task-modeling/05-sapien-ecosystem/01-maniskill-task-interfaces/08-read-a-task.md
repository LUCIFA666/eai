# 任务内部怎么读

前面几页一直从使用者接口看 ManiSkill：`gym.make()`、`reset()`、`step()`、`obs_mode`、`control_mode`。这已经足够跑任务和接训练。但如果想自定义任务，或者把一个任务迁移到别的仿真后端，就需要再往里看一层：一个 ManiSkill 任务内部通常由哪些部分组成？

这一页不要求读者马上改源码，只建立读代码的地图。以后看到一个新任务时，可以按这张地图去找它的场景、episode 初始化、成功判定和奖励。

## 一个任务通常包含哪些部分

以 PickCube 这类桌面操作任务为例，可以把任务内部拆成五块：

| 模块 | 它回答的问题 | 在 PickCube 里大致对应什么 |
|---|---|---|
| 场景构建 | 世界里有什么？ | 桌面、机器人、方块、目标标记、相机 |
| episode 初始化 | 每一轮从哪里开始？ | 方块位置、目标位置、机器人初始姿态 |
| 动作解释 | action 怎样作用到机器人？ | 由 `control_mode` 选择末端或关节控制器 |
| 观测构造 | 策略看到什么？ | `state` 向量或 `rgbd` 字典 |
| 评估与奖励 | 怎么判断进展和成功？ | 是否抓住、是否放到目标、机器人是否停稳 |

这五块和上一页的任务接口契约是对应的。`env_id` 选中了任务类；`obs_mode` 影响观测构造；`control_mode` 影响动作解释；`reward_mode` 影响奖励；`info["success"]` 来自评估逻辑。

## reset 不是简单清零

`reset(seed=0)` 不只是把时间归零。它还会根据任务规则初始化一个新的 episode：摆放物体、设置目标、重置机器人、更新任务相关状态。使用固定 seed 的意义，是让同一个随机过程可复现。

所以调试任务时，要区分两类问题：

| 现象 | 可能要看哪里 |
|---|---|
| reset 后物体不在预期位置 | episode 初始化、采样范围、坐标系 |
| 机器人初始姿态不对 | 机器人初始化、控制器默认状态 |
| 目标标记和成功判定不一致 | 目标位置采样、evaluate 逻辑 |
| 同一个 seed 每次结果不同 | 随机源、外部非确定性、并行环境初始化 |

## evaluate 比视频更接近任务语义

视频能让我们看到方块有没有被抓起来，但任务是否成功应该来自 evaluate 逻辑写入的 `info`。PickCube 的 `info` 里通常包含：

```text
is_grasped
is_obj_placed
is_robot_static
success
```

这些名字本身就透露了任务语义：不是“方块离桌面高一点”就一定成功，而是要同时考虑抓取、放置和机器人静止。读一个新任务时，优先找它往 `info` 里写了哪些子条件，这比盯着 reward 数值更快。

## reward 不一定等于最终目标

dense reward 往往是为了帮助学习：离物体近一点、抓住物体、靠近目标，都可能给策略提供梯度。success 则是评测时的离散判定。两者会相关，但不应该混为一谈。

写训练脚本时，可以让算法优化 reward；写评测脚本时，应该把 success 和子条件保存下来。这样失败时才能判断是探索不够、控制不稳，还是任务完成条件没有满足。

## 迁移任务时先迁移语义

如果把 PickCube 的思路迁移到 Genesis、Isaac Sim 或自建后端，最先要对齐的不是画面是否一模一样，而是任务语义：

```text
任务对象是什么？
初始状态怎样采样？
动作接口表示什么？
策略观测包含什么？
成功条件由哪些子条件组成？
日志和证据保存哪些字段？
```

这些语义对齐之后，再讨论资产格式、碰撞几何、相机渲染、接触参数和控制器实现，才不容易把“任务变了”和“后端实现变了”混在一起。

## 小结

- 一个 ManiSkill 任务内部可以按场景构建、episode 初始化、动作解释、观测构造、评估与奖励来读。
- `reset()` 会生成新的 episode 初始状态，不只是清零。
- `info` 里的子条件往往比 reward 更接近任务语义。
- 迁移到其他后端时，先固定任务语义，再讨论资产、控制和物理实现。

## 动手练习

打开一个 ManiSkill 任务源码，先不要改代码，只找三件事：它在哪里加载物体，在哪里设置 episode 初始状态，在哪里写 `success`。把这三处分别对应到本页的“场景构建、episode 初始化、评估与奖励”三块。
