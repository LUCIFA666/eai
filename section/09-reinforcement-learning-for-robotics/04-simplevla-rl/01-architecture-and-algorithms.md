## 10.4.1.1 导读：代码阅读结构与覆盖方式

### 项目定位

SimpleVLA-RL 做的事情很明确：给 VLA（视觉-语言-动作）模型做强化学习后训练。简单说就是——你先用示教数据把模型 SFT 到一个"还行"的水平，然后让它在仿真环境里自己跟自己练，通过成功/失败的反馈把成功率提上去。

这不是一个从零训练 VLA 的框架，而是站在 OpenVLA-OFT 这个预训练模型的肩膀上，用 RL 做"最后一公里"的提升。

### 代码仓库结构总览

拿到仓库先扫一眼目录，心里有个数：

```
SimpleVLA-RL/
├── examples/          # 训练启动脚本，各种 .sh
├── experiments/       # 实验配置，不同 benchmark 的参数
├── verl/              # 核心代码，数据、rollout、训练都在这
│   ├── workers/
│   │   ├── rob_dataset.py   # 数据集加载
│   │   └── rob_rollout.py   # 环境交互与轨迹采样
│   ├── trainer/
│   │   └── main_ppo.py      # 训练主入口
│   └── algorithm/
│       └── grpo.py          # GRPO 算法实现
├── LIBERO/            # LIBERO 基准环境（如果装了的话）
└── align.json         # W&B 等配置
```

实际读代码的时候，你会发现 SimpleVLA-RL 本身代码量不大——它更像是一个"胶水层"，把 veRL（强化学习框架）和 OpenVLA-OFT（VLA 模型）粘在一起，再加上机器人环境的适配。

### 阅读路线

建议按这个顺序读，从外到内：

1. **配置入口**：先看 `examples/` 里的 shell 脚本，知道训练是怎么启动的、参数从哪传
2. **数据管线**：`rob_dataset.py`，数据是怎么加载、怎么组织的
3. **Rollout**：`rob_rollout.py`，模型怎么和环境交互、怎么采轨迹
4. **Trainer**：`main_ppo.py`，整个训练循环长什么样
5. **策略优化**：`grpo.py`，GRPO 的 loss 具体怎么算

### 依赖栈

三个核心依赖，缺一不可：

- **veRL v0.2.x**：字节跳动做的 RL 框架，负责分布式训练、rollout 调度、策略更新。SimpleVLA-RL 是在这个框架上搭的。注意必须用 v0.2.x 分支，main 分支可能有不兼容的改动。
- **OpenVLA-OFT**：VLA 模型本体，带动作分块（action chunking）的版本。7B 参数，基于 LLaMA2。
- **Flash Attention**：加速注意力计算，省显存。7B 模型训练没这个基本跑不动。

## 10.4.1.2 骨干网络：OpenVLA-OFT

### 架构概览

SimpleVLA-RL 的"大脑"是 OpenVLA-OFT，整体结构分三块：

**视觉编码器**：两个并行的编码器

- **SigLIP**：负责语义特征，比如"这是杯子""那是红色"
- **DINOv2**：负责空间特征，比如"杯子在坐标 (x,y,z) 的位置"

两路特征拼起来，投影到 LLM 的嵌入空间里。

**语言模型**：LLaMA2-7B，同时处理语言指令和动作生成。输入是"图像特征 + 任务描述"，输出是一串动作 token。

**动作头**：把 LLM 的输出转成实际的机器人动作。

整个流程走下来就是：相机图像 → 两个视觉编码器 → 特征拼接投影 → 跟语言指令一起喂给 LLaMA2 → 生成动作 token 序列 → 解码成 7-DoF 机器人动作。

### 基于 token 的动作表示：为什么不用回归？

这是整个系统最关键的设计选择之一，也是 RL 能跑通的前提。

传统做法是**回归**：动作头直接输出 7 个连续值（6 个姿态 + 夹爪），用 L1 或 MSE loss。原始的 OpenVLA-OFT 一开始就是这么干的，用 MLP 头 + L1 loss。

SimpleVLA-RL 换了个思路——**基于 token**：每个动作维度被离散化成 256 个 bin，每个 bin 对应一个 token，就像 LLM 生成文字一样生成动作。动作分块（action chunking）再把多个时间步的动作打包成一个序列一次性输出。

举个例子：

- LIBERO：分块大小 = 8 步，每步 7 个维度，总共 8 × 7 = 56 个 token？还是说每个维度的 token 化方式不同？这个细节等读到 `action_tokenizer.py` 的时候再确认。核心思想不变：动作被离散化成了 token，跟 NLP 里的词 token 一个道理，这样就能直接用大模型的生成范式来做动作预测。

### 为什么基于 token 对 RL 很重要？

三个原因：

**1. 自然的概率分布**

每个 token 在词表上都有一个概率分布，算对数概率很方便——这是策略梯度的基础。用回归的话，你得自己假设一个分布（比如高斯），但这个假设往往不对。

**2. 跟 GRPO 天然兼容**

GRPO（以及 PPO、REINFORCE 这些）都要算策略比 $\pi_{\text{new}}(a|s) / \pi_{\text{old}}(a|s)$。基于 token 的话，这个比值直接从 logits 算出来就行。回归的话，你得额外参数化一个分布。

**3. 自带探索**

采样的时候把温度调高，模型自然就会尝试更多样的动作——不用额外加噪声。温度 1.6 的时候，模型就足够"有创造力"了，能试出一些新奇的动作。

### 跟原始 OpenVLA-OFT 的对比

| 特性 | 原始 OpenVLA-OFT | SimpleVLA-RL |
|------|-----------------|-------------|
| 动作表示 | MLP 头，连续值 | 基于 token，离散化 |
| 损失函数 | L1 回归 | 交叉熵（SFT）+ GRPO（RL） |
| 视角 | 多视角 | 单视角（简化计算） |
| 能不能做 RL | 难，得改动作头 | 原生支持 |

换成单视角也是有考量的。多视角三维信息更好，但单视角大幅降低了 RL 训练的计算成本——而且只要训练够多，单视角也能达到差不多的效果。

## 10.4.1.3 GRPO 优化算法

### 什么是 GRPO？

GRPO（Group Relative Policy Optimization，群体相对策略优化）最早是 DeepSeek 团队给大模型 RLHF 做的，SimpleVLA-RL 是最早把它用到机器人操作上的工作之一。

核心思路跟 PPO 不一样：PPO 需要一个单独的 Critic 网络来估计价值函数，GRPO 不用——它直接在同一个查询的多个样本之间互相比较，算出"相对优势"。

### GRPO 是怎么工作的

一步一步说：

**步骤 1：采样**

对于每个查询（初始状态 + 任务指令），模型生成 G=8 条不同的轨迹（靠高温采样驱动多样性）。每条轨迹就是一串动作 token。

**步骤 2：评估**

把这 8 条轨迹都丢到仿真环境里跑一遍，给二元奖励：

```python
# 伪代码
rewards = []
for trajectory in trajectories:
    success = env.evaluate(trajectory)
    rewards.append(1.0 if success else 0.0)
# 比如 rewards = [1, 0, 1, 1, 0, 0, 1, 0]
```

**步骤 3：计算群体相对优势**

把组内的奖励做个归一化：

```python
mean_r = mean(rewards)   # = 0.5
std_r = std(rewards)     # ≈ 0.535
advantages = [(r - mean_r) / std_r for r in rewards]
# 成功的轨迹拿到正优势，失败的拿到负优势
```

**步骤 4：策略更新**

最大化这个目标：

$$
L = \mathbb{E}\left[ \min\left( \text{ratio} \cdot A, \; \text{clip}(\text{ratio}, \; 1-\epsilon_{\text{low}}, \; 1+\epsilon_{\text{high}}) \cdot A \right) \right]
$$

其中：

- $\text{ratio} = \pi_{\text{new}}(a|s) / \pi_{\text{old}}(a|s)$，新旧策略的概率比
- $A$ 就是第 3 步算出来的优势
- $\epsilon_{\text{low}} = 0.2$，$\epsilon_{\text{high}} = 0.28$

### 非对称裁剪：一个微妙但厉害的设计

这是论文里一个挺重要的技术点。标准 PPO 的裁剪是对称的：$\epsilon = 0.2$，范围就是 $[0.8, 1.2]$。SimpleVLA-RL 用的是非对称的：$[0.8, 1.28]$。

为什么这么设计？想一个具体场景：

- **罕见但成功的动作**：旧策略给了很低概率的某个动作（比如"推一下再抓"而不是直接抓），但最后居然成功了。这时候 ratio 很大（$\pi_{\text{new}} \gg \pi_{\text{old}}$）。对称裁剪的话，上限卡在 1.2——策略只能"温和地"提高这个动作的概率。非对称裁剪把上限放宽到 1.28，策略就能更激进地提升那些没试过但效果好的动作。
- **常见但失败的动作**：ratio 变小（$\pi_{\text{new}} < \pi_{\text{old}}$）。下限还是 0.8——降低概率，但降得没那么快，不会一下子把动作砍没了。

简单说就是：涨得快，降得慢。鼓励探索，尤其是在二元奖励信号比较弱的时候。

### 没有 KL 散度项

传统 PPO 通常会加一个 KL 散度项，防止新策略跟旧策略差太远：

$$
L = L_{\text{clip}} - \beta \cdot \text{KL}(\pi_{\text{new}} \parallel \pi_{\text{old}})
$$

SimpleVLA-RL 直接把 KL 项去了（$\beta = 0$）。理由是：

1. **省显存**：不用存一份参考模型（7B 参数），每张卡省约 14GB 显存。
2. **SFT 已经打好了基础**：SFT 之后的 VLA 模型已经有了"合理"的策略——知道怎么靠近物体、怎么移动抓手。RL 只是微调，不需要剧烈改变。
3. **实验说话**：加了 KL 并没有更好，反而可能因为限制了探索而降低性能。

### GRPO vs PPO 对比

| 特性 | PPO | GRPO |
|------|-----|------|
| Critic 网络 | 需要（额外参数、额外训练） | 不需要 |
| KL 正则化 | 常用 | 不需要 |
| 优势估计 | GAE（需要值函数） | 群体相对（组内比较） |
| 内存占用 | 高（策略 + Critic + 参考模型） | 低（只有策略） |
| 超参数 | 多（GAE lambda、Critic 学习率、KL beta 等） | 少（eps_low、eps_high、温度） |
| 实现复杂度 | 高 | 低 |

GRPO 用优势估计的准确性（PPO 的 Critic 更准）换来了简洁和高效。在 7B 参数的 VLA 模型上，去掉 Critic 网络能省约 14GB 显存——足够把 batch size 开大一些，或者少用几张 GPU。

## 10.4.1.4 关键技术：动态采样与二元奖励

### 动态采样：一个听起来简单但决定成败的技巧

#### 问题：梯度消失

回想一下 GRPO 的第三步——计算优势。如果 8 条轨迹全成功了呢？

```python
rewards = [1, 1, 1, 1, 1, 1, 1, 1]
mean_r = 1.0
std_r = 0.0   # 全都一样！
advantages = [0, 0, 0, 0, 0, 0, 0, 0]   # 没有梯度信号！
```

全失败也是一样的。每条轨迹的优势都是 0，平均值也是 0——模型什么都学不到。

这个问题在二元奖励下特别严重。如果是密集奖励（0.1、0.3、0.7、0.9 这种），就算全成功了奖励也不一样，优势不会是零。但二元奖励只有两个值，很容易出现全 0 或全 1 的情况。

#### 解决方案：不行就重来

SimpleVLA-RL 的做法很直接——动态采样。每个 batch 如果所有轨迹奖励都一样（全成功或全失败），就把这个 batch 扔掉，重新采样。

```python
# 伪代码
while True:
    trajectories = model.generate(query, num_samples=8, temperature=1.6)
    rewards = [env.evaluate(t) for t in trajectories]
    
    if len(set(rewards)) > 1:  # 有成功也有失败
        break  # 这个 batch 有用
    
    # 否则，重新采样
```

这个技巧听着太简单了，像是个 trick。但没有它，RL 训练根本就不收敛。论文的消融实验说，去掉动态采样，性能掉 15-20%。

#### 直觉理解

可以把动态采样想成"选合适难度的练习题"。如果题太简单（全做对），你学不到新东西。如果题太难（全做错），你也学不到。在"刚好有可能做对"的边界上，学得最多——动态采样保证的就是这个。

### 二元奖励：简单但够用

#### 奖励是给整条轨迹的

一个细节：奖励 $R=1$ 或 $R=0$ 是分配给轨迹上所有 token 的，不是只给最后一个 token。

```python
# 如果轨迹成功
token_rewards = [1, 1, 1, 1, ..., 1]  # 所有 token 都拿 R=1
# 如果轨迹失败
token_rewards = [0, 0, 0, 0, ..., 0]  # 所有 token 都拿 R=0
```

为什么不给每个 token 单独分配奖励？因为我们不知道哪个 token 是关键的。一条 2048 个 token 的轨迹里，可能第 500 个 token（决定从哪个角度下手）决定了成败，但我们不知道。给所有 token 相同的奖励，GRPO 会通过群体相对优势自动找出哪些 token 的概率该涨、哪些该降。

#### 跟密集奖励比怎么样

| 特性 | 二元奖励 | 密集奖励 |
|------|---------|---------|
| 设计工作量 | 自动（任务成功检测器就行） | 每个任务都要专家设计 |
| 容易被 hack 吗 | 很难 | 很容易 |
| 梯度信号 | 弱（需要动态采样补） | 强 |
| 泛化性 | 高（跟任务无关） | 低（任务特定） |
| 可扩展性 | 好 | 差（每个任务都得重新设计） |

二元奖励用更弱的即时信号，换来了更好的可扩展性和鲁棒性——配上动态采样，信号弱的问题基本就补上了。

### 温度：探索与利用的平衡

SimpleVLA-RL 在生成轨迹（rollout）的时候用温度 1.6，推理的时候用温度 0（贪婪采样）。

为什么是 1.6？

- 温度 1.0 是"默认值"，概率分布就是模型原本的样子
- 温度 > 1.0 会把分布拉平，增加稀有 token 的概率
- 温度 1.6 时，最常见的 token（比如"往前移动"）仍然概率最高，但稀有 token（比如"往左推一下"）的概率比温度 1.0 时明显高了

结果就是：模型会尝试更多不同的策略，而不是只会一种方法。

1.6 是个比较合适的值——足够高能探索，但又不会高到动作完全随机（温度 > 2.0 一般就太吵了）。

两种模式分开很重要：

| 阶段 | 温度 | 目的 |
|------|------|------|
| 训练（rollout） | 1.6 | 最大化探索，收集多样的轨迹 |
| 推理（部署） | 0（贪婪） | 最大化利用，选最优动作 |

训练和推理的目标不一样。训练需要多样性来发现新策略。推理需要一致性来达到最高的成功率。
