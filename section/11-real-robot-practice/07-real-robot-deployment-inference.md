# 服务器远程推理

对于ACT和DP等基于模仿学习的模型，机载边缘推理设备的算力足够进行策略的部署。因此这里以Aloha双臂上运行的 $pi_0$ 模型为例进行服务器远程推理方法的讲解。

整个系统采用分布式架构，计算密集型的模型推理运行在机外强算力端（服务器），而低延迟的动作执行运行在机器人边缘端（车载电脑）。两者通过基于 WebSocket 协议的 `WebsocketPolicyServer` 实现流式数据的双向长连接通信。通过将计算密集的视觉语言动作模型（VLA）部署在强算力服务器上，机器人机载电脑可以不使用大功率的高性能显卡，实现边缘设备的轻量化。

本节介绍如何将传统的单机控制流重构为**机外远程推理、边缘端实时执行**的分布式真机部署架构。

---

## 1. 分布式架构介绍

在传统的单机推理中，任务环境（`TASK_ENV`）与模型（`Model`）在同一台机器上高频交互。在分布式重构后，两者的职责进行了彻底的解耦：

```text
 ┌──────────────────────────────────────┐          ┌──────────────────────────────────────┐
 │       机器人边缘端 (Client / Env)     │          │        机外强算力端 (Server / Model)  │
 ├──────────────────────────────────────┤          ├──────────────────────────────────────┤
 │ 1. 采集三路相机 RGB 与机械臂当前关节角  │          │ 1. 接收多模态观测数据                 │
 │ 2. 通过 WebSocket 发送原始观测数据     │ ───► ───►│ 2. 注入自然语言指令                   │
 │                                      │          │ 3. 维护历史观测滑动窗口                │
 │                                      │          │ 4. GPU 强算力前向推理生成 Action       │
 │ 3. 解析服务器传回的动作块 (Chunk)      │ ◄─── ◄───│ 5. 截取 pi0_step 步长动作通过 WS 下发  │
 │ 4. 纯硬件驱动执行                     │          │                                       │
 └──────────────────────────────────────┘          └──────────────────────────────────────┘

```

---

## 2. 机外强算力端推理发送流程

服务器端作为整个分布式控制系统的“大脑”，统一托管了原单机架构中的 `PI0` 模型实例。它不仅承担着高负载的 GPU 前向计算，还全面接管了语言条件注入与时序上下文窗口的维护工作。通过 `WebsocketPolicyServer` 建立的长连接，服务器能够以极低的通信开销响应边缘端的请求，并在维持时序连贯性的同时，流式下发高精度的动作轨迹。

在分布式重构后，原本运行在机器人本地的 `model.set_language(instruction)` 和 `model.update_observation_window()` 被完全收拢至服务器端隐式执行，从而将边缘端从繁重的状态追踪中解放出来。

当远程服务器接收到机器人的首帧连接请求或任务重置信号时，底层的策略配置会自动解析当前的任务文本指令（如具体的物体抓取或操作口令），并将其作为条件特征注入 VLA 大模型的语言嵌入层，以此确立整个操作序列的语义导向。

与此同时，服务器会在内存中为每个处于激活状态的机器人连接独立维护一个滑动窗口队列。每当边缘端上传最新的单帧观测数据，服务器并不会孤立地对其进行评估，而是将其动态追加到该机器人的时序队列中。通过这种服务器端内部的滚动 FIFO 机制，多视角的视觉特征和本体关节状态能够在时间维度上形成连续的上下文缓存，确保大模型在后续的前向传播中具备精准捕捉动态物理交互的时序连贯性。

当边缘端的多模态数据通过网络抵达后，服务器将立即在后台触发核心的异步推理响应循环。服务器利用 `msgpack_numpy` 对高密度的网络字节流进行高速反序列化，将其近乎无损地还原为 GPU 可直接读取的多维张量。

```python
# 服务器端的核心响应循环
obs = msgpack_numpy.unpackb(await websocket.recv())
action = self._policy.infer(obs) # 内部包含 PI0 的 get_action() 并在内部更新 Window
await websocket.send(packer.pack(action))

```

在核心响应流中，服务器在阻塞等待 `await websocket.recv()` 唤醒后，会直接调用 `self._policy.infer(obs)` 接口。在 `infer` 方法内部，服务器首先将新到的观测值压入前述的滑动窗口，随后将整个时序上下文送入 `PI0` 模型的神经网络中进行并行计算。

虽然 `PI0` 模型基于大模型架构原生会预测出一个跨越较长时空范围的宏观动作轨迹，但为了兼顾真机执行的实时反馈效率与预测精度，服务器会根据预设的配置文件，利用切片操作严格截取未来前 `pi0_step` 步长的一组紧凑动作块（Action Chunk）。这一截断后的动作矩阵随即被 Packer 重新压缩为高密度的二进制数据流，通过既有的全双工 WebSocket 通道流式闪送回边缘端，从而完成一次高频的“感知-推理-响应”闭环。

## 3. 机器人边缘端：流式采集与动作执行环

机器人端的电脑起到的作用为一个高频输入输出节点。它不再运行任何神经网络，只负责运行一个轻量级的 WebSocket 客户端连接环，同时进行相机数据和关节数据的打包发送与推理结果的接收和解析。

机器人端定时（例如 $20\text{Hz}$）捕获传感器外设，并严格按照模型所需的对齐格式进行标准化打包：

同时提取头部相机（head_camera）、右腕相机（right_camera）和左腕相机（left_camera）的三路实时 RGB 矩阵。
提取双臂当前的绝对关节向量（`joint_action["vector"]`）。

```python
# 机器人边缘端：传感器数据编码
input_rgb_arr = [
    observation["observation"]["head_camera"]["rgb"],
    observation["observation"]["right_camera"]["rgb"],
    observation["observation"]["left_camera"]["rgb"],
]
input_state = observation["joint_action"]["vector"]

# 包装后通过 WebSocket 发送给服务器
await websocket.send(packer.pack({"rgb": input_rgb_arr, "state": input_state}))

```

当机器人端通过 WebSocket 接收到服务器回传的二进制数据后，利用 `msgpack_numpy` 将其还原为形状为 `[pi0_step, action_dim]` 的 NumPy 动作块（Action Chunk）。

机器人端紧接着启动一个本地的硬件循环。在此循环中，机器人不再进行推理，只执行这一批动作：

```python
# 机器人边缘端：纯动作执行环
actions = packer.unpackb(await websocket.recv()) # 接收长度为 pi0_step 的动作块

for action in actions:
    # 1. 动作反归一化 (还原为真实物理弧度)
    physical_action = action * scale + offset 
    
    # 2. 底层总线驱动 (通过 Dynamixel SDK 或 ROS2 Controller 发送给电机)
    TASK_ENV.take_action(physical_action) 

```

当这一批次（`pi0_step` 步）动作在真机上全部顺序执行完毕后，机器人端会立即采集执行结束时最新的相机图像和关节向量，重新执行 `encode_obs`，并发起下一次 WebSocket `send` 请求。

通过这种边缘采集发送 $\rightarrow$ 服务器大模型推理 $\rightarrow$ 边缘纯执行 $\rightarrow$ 再次采集发送的分布式闭环，既保证了机器人的本地轻量化与实时响应，又赋予了真机拥有机外强算力服务器带来的全量大模型智能。
