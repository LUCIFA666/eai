# 力控证据链

> 难度：[高级] | 预计用时：55 分钟
> 先修：[接触事件与滑移检测](06-contact-slip.md)

目标：把力觉数据从”控制器内部信号”提升为可复盘、可评测、可触发安全动作的证据链。

## 先弄懂 wrench（力螺旋）

**wrench（力螺旋）**：同时包含力和力矩的六维量。F/T 传感器输出的就是 wrench。

```
wrench = [Fx, Fy, Fz, Tx, Ty, Tz]
```

其中：
- `Fx, Fy, Fz`：三个方向的力（牛顿）
- `Tx, Ty, Tz`：绕三个轴的力矩（牛顿·米）

wrench 必须记录在哪个坐标系下才有意义。同一个力在不同 frame 下坐标值不同。

**TCP（Tool Center Point）**：工具中心点，夹爪末端的参考位置。力矩通常相对于 TCP 计算。

做接触任务时，力控像机器人手上的“压感与顺从性”。你不是只关心“力大不大”，而是关心“沿哪个方向有力”“什么时候开始有力”“这个力在当前阶段是合理还是危险”。所谓证据链，就是把力信号、接触阶段、末端位姿、视频片段和最终结果连起来，让一次失败能被解释成“没碰到”“碰到了但方向不对”“顶住了但卡死”“已经过载必须停机”。

## 本页目标

这一页读完后，我们希望能一起把下面几件事说明白：

- 解释力阈值、滤波、坐标变换和控制频率为什么必须一起设计。
- 区分没接触、轻接触、过载、卡住和滑移在力曲线上的不同迹象。
- 为擦拭、插孔、推门或拧盖任务写出关键力觉指标。
- 设计一份与视频、关节轨迹同步的力控日志。

## 力数据不是只看一个阈值

| 任务真正关心的量 | 例子 |
|---|---|
| 力的大小 | 法向接触是否建立 |
| 力的方向 | 是在沿法向压入，还是沿切向刮擦 |
| 力随时间的变化 | 是平稳接触，还是突然冲击 |
| 力在哪个 frame 下表达 | TCP、工具系还是 base 系 |
| 与动作阶段的对应 | 接近、接触、插入、退出 |

```text
接近阶段:      force ~ 0
首次接触:      force suddenly rises
稳定插入/擦拭: force stays in a band
卡住/过载:     force keeps rising or oscillates
退出阶段:      force drops back near 0
```

只有把时间、方向和阶段一起看，力曲线才有可解释性。

## 为什么坐标变换是硬要求

腕部六维力传感器常先给你传感器坐标系下的 `Fx, Fy, Fz, Tx, Ty, Tz`。但任务关心的往往是工具系或世界系里的力：

| 表达 frame | 适合判断什么 |
|---|---|
| sensor frame | 原始读数、驱动调试 |
| TCP frame | 工具前进方向上的压入力、切向摩擦 |
| base/world frame | 与环境平面或重力方向关联 |

如果在 `sensor frame` 里设置“向下压 5 N”的阈值，而传感器安装角度偏了 30°，这个阈值本身就没有任务意义。

## 一个最小力日志结构

```yaml
force_control_sample:
  timestamp: 2026-05-26T11:40:28.991Z
  task_phase: insert
  frame_id: tool0
  wrench:
    force_n: [0.4, -0.2, 4.8]
    torque_nm: [0.01, 0.08, -0.02]
  filtered:
    force_norm_n: 5.82
    normal_force_n: 5.74
    tangential_force_n: 0.45
  controller:
    target_force_n: 6.0
    control_rate_hz: 250
  status: nominal_contact
```

这份结构把原始数据、滤波结果、目标值和当前阶段放在一起，足够支撑大多数复盘。

## 四类任务看哪些指标

| 任务 | 最关键指标 | 常见失败迹象 |
|---|---|---|
| 擦拭 | 法向力稳定在窄带内 | 力忽高忽低，接触不连续 |
| 插孔 | 轴向力 + 横向力/力矩 | 轴向力上升但位移不进，说明卡住 |
| 推门 | 把手/门板方向上的切向力 | 力大但门角度没变，可能锁住或方向不对 |
| 拧盖 | 扭矩与角位移关系 | 扭矩尖峰但无旋转，说明打滑或卡死 |

重点不是“把所有量都看一遍”，而是先定义任务成功必须依赖哪一类物理证据。

## 一个简单的失败判定逻辑

```python
# 根据阶段和力曲线判断失败类型
def classify_force_failure(normal_force, tangential_force, progress_delta):
    if normal_force < 0.5 and progress_delta <= 0.0:
        return "no_contact"
    if normal_force > 8.0 and progress_delta <= 0.0:
        return "jammed_or_overload"
    if tangential_force > 2.0 and progress_delta < 0.0:
        return "slip_or_scrape"
    return "nominal"

# 预期输出:
# 'no_contact' / 'jammed_or_overload' / 'slip_or_scrape' / 'nominal'
```

这里把“力曲线”和“任务是否推进”结合起来了。只看力，不看位移，很容易把正常接触误报为失败。

## 滤波与控制频率的关系

| 设计项 | 过强会怎样 | 过弱会怎样 |
|---|---|---|
| 低通滤波 | 尖峰被抹平，接触发生得太晚才看见 | 噪声太大，阈值抖动 |
| 控制频率 | 太低会错过短暂碰撞 | 太高但日志不跟，会难以复盘 |
| 事件抽样率 | 太稀会看不到阶段转换 | 太密则存储与分析成本高 |

教学时你至少要能回答：我的原始传感器频率是多少、控制循环是多少、最终落盘是多少。

## 力控证据链的完整样子

```text
视频帧 t=12.4s
   + 末端位姿
   + 关节轨迹
   + wrench(tool0)
   + task_phase=insert
   + outcome=jammed_or_overload
```

有了这条链，失败报告才不再是“机器人好像卡住了”这种模糊描述。

## 练习

### [观察] 给一次接触任务定义证据链

1. 在“插孔”或“擦拭”中任选一个任务。
2. 画出需要同步保存的五类信号：视频、位姿、力、控制目标、任务阶段。
3. 指出哪一种失败只能靠力觉看出来。

完成后，可以先用下面几条检查这一部分是否已经到位：
- 能说出至少一个需要在 `tool frame` 下解释的力分量。
- 能解释为什么视频本身不足以区分“卡住”和“没接触”。

### [复现] 写一份失败复盘模板

1. 设计一个 YAML 或表格模板，字段至少包含 `timestamp`、`task_phase`、`wrench`、`pose_delta`、`failure_code`。
2. 分别填入“没接触”“过载”“卡住”三种 case 的示例值。

完成后，可以先用下面几条检查这一部分是否已经到位：
- 模板能支持事后人工判断失败类型。
- 能根据模板决定继续执行、重试还是停机。
