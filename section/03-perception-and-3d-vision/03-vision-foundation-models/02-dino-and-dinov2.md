# DINO 与 DINOv2

> 难度：[中级] | 预计用时：75 分钟
> 先修：[CLIP 与 SigLIP](01-clip-and-siglip.md)
> 阅读提示：本页重点是 patch feature、dense feature 和局部对应。

目标：讲清 DINO 与 DINOv2 这类自监督视觉表征模型在机器人里到底解决什么问题，以及为什么它们虽然也输出 feature，却不应该被简单理解成“另一个 CLIP”。

## 先建立直觉

假设任务不是“找红色杯子”，而是：

- 在连续视频里一直跟住同一把抽屉把手
- 找到和演示视频中最像的那一块局部结构
- 判断这一帧里的边缘是不是上一帧同一个物体边缘

这时系统最需要的不是一句语言匹配分数，而是：

**哪里和哪里在局部视觉结构上更相似。**

这正是 DINO 一类模型最擅长的方向。

## DINO 在回答什么问题

与 CLIP 的“图文对齐”不同，DINO 更偏向：

**从图像内部学习稳定的视觉结构表示。**

它并不天然处理文本查询。  
它更擅长的是：

- 图像内部哪些局部结构相似
- 两张图之间哪些局部区域能对应起来
- 哪些局部特征在视角变化后仍然稳定

因此，DINO 的典型问法不是“它是不是红色杯子”，而是“这一块和那一块是不是同一个局部结构”。

## 什么是 patch feature，并立刻接例子

`patch feature` 可以先理解成：

**把图像切成很多小块，每一块都有自己的特征表示。**

立刻看例子就更直观：

- 一张抽屉图像中，把手附近的一块 patch 会得到一个特征向量。
- 另一张图像中，类似的把手区域也会得到一个特征向量。
- 如果两块区域局部结构相似，它们的 feature 通常也更接近。

所以 patch feature 关注的是“局部长得像不像”，不是整张图的语言语义。

## 什么是 dense feature，并立刻接例子

`dense feature` 可以理解成：

**为图像中很多空间位置都保留特征表示。**

例子如下：

- 当前帧中的把手边缘有一组特征
- 上一帧中同一把手边缘也有一组特征
- 比较这些特征后，可以判断局部对应关系是否稳定

因此 dense feature 特别适合：

- 局部匹配
- 视频跟踪
- 跨视角对应
- 边界与分割的稳定化

术语讲完后，马上接结论：  
patch feature 是“按局部块提特征”，dense feature 是“按大量空间位置保留特征”，两者都服务于局部结构对应。

## DINO 的训练直觉

DINO 属于自监督视觉表征路线。  
对初学者来说，最重要的直觉不是公式，而是下面这句话：

**模型在没有依赖人工文本标注的前提下，也能学出稳定的视觉结构表示。**

这类训练方式的结果是：

- 模型会更关注图像内部的结构与一致性
- 局部区域的表示在视角变化、轻微裁剪后仍然更稳定
- 特征更适合作为对应和匹配的证据

DINOv2 可以看成在数据规模、训练稳定性和特征质量上进一步强化后的版本。  
从本章角度，它们承担的是同一类职责：为图像局部结构提供更稳的表征。

## 为什么 DINO 不能简单看成“另一个 CLIP”

表面上看，CLIP 和 DINO 都会输出 feature。  
但输出 feature 不等于解决同一种问题。

两者最根本的差异是：

- CLIP / SigLIP：更偏图文语义对齐
- DINO / DINOv2：更偏图像局部结构表征

立刻接两个例子：

- 如果任务是“找桌上的红色杯子”，优先想到的是 CLIP。
- 如果任务是“在连续帧里跟住同一块把手区域”，优先想到的是 DINO。

这两个任务需求完全不同，因此不该用同一种模型去硬做。

## DINO 在机器人里最常见的用法

### 1. 跟踪辅助

连续帧中，系统需要判断上一帧和下一帧的某块区域是否仍是同一对象局部。  
DINO 的 dense feature 很适合作为这类判断的证据。

### 2. 局部对应

当系统需要把演示中的某块交互区域对到当前图像时，重点不是整体语义，而是局部结构相似度。  
这时 DINO 比纯语义模型更自然。

### 3. 稳定分割或位姿

如果分割边界在多帧之间跳动，局部 feature 可以帮助判断“这一块到底是不是同一条边、同一片表面、同一块前景”。

## 一张对比表把 CLIP 和 DINO 分开

| 维度 | CLIP / SigLIP | DINO / DINOv2 |
|---|---|---|
| 主要问题 | 图文语义匹配 | 图像局部结构匹配 |
| 典型输入 | 图像 + 文本 | 图像 |
| 典型输出 | image/text embedding | patch feature、dense feature |
| 天然支持文本查询 | 是 | 否 |
| 更适合 | 候选重排序、开放词汇检索 | 跟踪、对应、局部匹配 |
| 不能直接替代 | 几何恢复 | 文本语义查询 |

如果只记一句话：

**CLIP 更像语义检索器，DINO 更像局部结构特征地图。**

## 一个最小 observation 记录应该怎么写

与其把所有 feature 都写成“模型分数”，不如把来源区分清楚。

例如语义筛选证据：

```yaml
semantic_feature_record:
  object_id: mug_candidate_03
  query: red mug
  feature_type: clip_embedding
  feature_ref: runs/04-perception/features/mug_candidate_03_clip.npy
  similarity_score: 0.79
```

再例如局部对应证据：

```yaml
dense_feature_record:
  track_id: handle_track_02
  feature_type: dino_dense_feature
  feature_ref: runs/04-perception/features/handle_track_02_dino.npy
  match_score: 0.72
```

这两类记录看起来都像 feature，但语义完全不同：

- `similarity_score` 说明文本和候选是否接近
- `match_score` 说明两个局部结构是否接近

## DINO 仍然不能直接给出什么

DINO 虽然非常适合做局部对应，但它默认仍然不直接等于：

- 文本查询结果
- 几何真值
- 刚体 `pose`
- 接触点规划结果

尤其要避免一个常见误用：

**局部 feature 很稳定，不等于已经恢复出了可执行的 6D 位姿。**

## 常见误解

| 误解 | 为什么错 |
|---|---|
| “DINO 也是 feature，所以和 CLIP 差不多” | 两者服务的问题类型不同 |
| “有 dense feature 就等于有 pose” | 局部表征不是刚体位姿 |
| “DINO 可以直接接文本查询” | 它默认不是图文对齐模型 |
| “只保留最终标签就够了” | 局部对应证据需要保留来源和分数 |

2. 为什么 DINO 更适合“哪里像哪里”，而不是“谁更像文本描述”？
3. 为什么局部对应做得好，仍然不等于几何执行结果已经准备好？

## 练习

### [观察] 为三个任务选择模型

判断下面三个任务应该优先考虑哪类模型：

1. “找桌上的红色杯子”
2. “在连续帧中跟踪同一块抽屉把手区域”
3. “给多个候选框按语言目标重新排序”

完成后，可以先用下面几条检查这一部分是否已经到位：
- 能明确区分语义选择和局部对应。

### [复现] 写一份局部对应记录

为“连续两帧中的同一把手区域”写一份 feature 记录，至少包含：

- `track_id`
- `feature_type`
- `feature_ref`
- `match_score`

完成后，可以先用下面几条检查这一部分是否已经到位：
- 记录体现的是局部结构对应，而不是文本语义匹配。
