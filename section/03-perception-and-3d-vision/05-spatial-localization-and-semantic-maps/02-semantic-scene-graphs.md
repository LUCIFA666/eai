# 语义地图与 3D 场景图

> 难度：[进阶] | 预计用时：50 分钟
> 先修：[空间定位与建图](01-spatial-localization-mapping.md)
> 建议：把本页理解成“地图语义层”，它的重点不是 3D 检测本身，而是让地图变成任务可查询记忆。

目标：理解语义地图与 3D 场景图怎样把几何地图升级成任务可用记忆，知道开放词汇 3D 语义、实例融合和场景图查询如何支撑长程移动操作。

## 先建立直觉

几何地图能告诉机器人：

- 哪里有墙。
- 哪里是桌面。
- 哪些区域是空的，哪些是占据的。

但很多任务需要的不是“几何上可到”，而是“语义上该去哪里”：

- 去厨房台面找红色杯子。
- 回到刚才看到抽屉把手的柜体区域。
- 在“冰箱左边的台面上”继续执行上一步动作。

这时光有几何地图不够，因为任务开始依赖：

- 物体实例是谁。
- 区域的语义是什么。
- 这些对象之间的空间关系是什么。

这就是语义地图与 3D 场景图要补上的那一层。

## 本页目标

这一页读完后，我们希望能一起把下面几件事说明白：

- 解释为什么几何地图还不足以支撑长程任务检索。
- 区分语义地图和 3D 场景图的职责边界。
- 理解开放词汇 3D 语义、实例融合和关系查询怎样串起来。
- 写出一份最小 `scene_graph_query_result`，并知道什么时候图结构已经失真到不该继续用。

## 语义地图和场景图到底差在哪

| 结构 | 更偏回答什么 |
|---|---|
| 语义地图 | 哪些区域、体素或局部表面属于什么语义类别 |
| 3D 场景图 | 哪些对象或区域存在、它们之间是什么关系 |

可以把它们粗略理解成：

- 语义地图更像“带标签的空间底图”。
- 3D 场景图更像“对象和关系的数据库”。

它们通常是配合出现的，而不是二选一。

## 从几何地图升级到任务地图的典型链路

```text
geometry map
  -> object / region proposals
  -> semantic labeling
  -> multi-view instance fusion
  -> relationship building
  -> graph query for tasks
```

这里最关键的不是单次检测有多强，而是：

- 同一个对象在多次观测里是不是能被融合成同一实例。
- 语义标签是不是能在地图坐标系里长期稳定。
- 查询结果是不是能回到真实几何位置。

## 开放词汇 3D 语义为什么重要

传统语义地图常依赖固定类别，如 `chair / table / wall`。  
但具身任务里常常需要更开放的语义目标：

- “红色杯子”
- “左边那个抽屉把手”
- “微波炉旁边的白色盒子”

所以近年的语义地图越来越强调：

- 借助开放词汇检测或图文对齐模型给 2D 或 3D 区域赋语义。
- 把这些语义结果再融合进长期地图。

这里真正难的不是“给某一帧贴标签”，而是“让标签在空间里长期成立”。

## 实例融合为什么是关键步骤

如果没有实例融合，场景图很快会坏掉：

- 同一只杯子被写成 5 个节点。
- 同一张桌子在不同视角下被重复计数。
- 物体移动后，旧实例和新实例混在一起。

所以场景图系统通常至少要做：

- 同视角内去重。
- 跨视角实例关联。
- 对象状态更新或失效管理。

这也是为什么场景图不是“检测结果堆成列表”，而必须有实例级维护逻辑。

## 场景图最有价值的地方：关系查询

对象列表已经比几何地图更有任务价值，但场景图真正的强项是关系层：

- `on(top_of)`
- `inside`
- `next_to`
- `left_of`
- `attached_to`

这类关系能让上层任务系统从“找一个对象”升级到“找一个满足关系约束的对象”。  
例如：

- 找“台面上、冰箱左边、靠近咖啡机”的杯子。
- 找“抽屉内部”的盒子。
- 找“桌子旁边”的充电座。

## 它在移动操作里怎样使用

一条更贴近系统的链路通常是：

```text
language query
  -> semantic / graph query
  -> candidate objects or regions
  -> map-frame pose or region
  -> navigation / manipulation planner
```

这说明场景图的价值不是“多一个花哨结构”，而是让语言任务真正落到地图中的几何实体上。

## 一个最小场景图查询结果

```yaml
scene_graph_query_result:
  query: "red mug on kitchen counter"
  map_id: kitchen_map_v3
  frame_id: map
  candidates:
    - node_id: object_mug_07
      label: red mug
      relation_context:
        support: counter_02
        left_of: coffee_machine_01
      pose:
        xyz_m: [2.13, -0.48, 0.93]
        quat_xyzw: [0.0, 0.0, 0.09, 0.99]
      confidence: 0.78
  failure_code: null
```

这份结构说明一件事：  
场景图最终也要回到 `map` 坐标系中的几何落点，不然下游仍然无法行动。

## 什么时候语义地图或场景图不能继续用

下面这些情况，图结构虽然“还在”，但通常不该继续被下游当真：

| 情况 | 风险 |
|---|---|
| 定位链已漂移 | 图里的对象关系落在错误位置 |
| 同一实例重复裂变成多个节点 | 查询结果不稳定，排序失真 |
| 环境已变化但旧图未更新 | 找到的是历史对象，而不是当前对象 |
| 开放词汇标签歧义太强 | 语义节点本身不可靠 |

因此场景图和对象 pose 一样，也需要自己的更新时间、来源和失败状态。

## 常见误区

| 误区 | 为什么错 |
|---|---|
| “语义地图就是给占据栅格上色” | 真正难点在长期一致性和实例维护 |
| “场景图就是对象列表加几条边” | 关系只有在稳定几何和实例融合上才有意义 |
| “只要 2D 检测够强，场景图自然就对” | 2D 强不等于 3D 融合和长期维护强 |
| “图里有对象名就能直接导航” | 下游仍然需要回到 `map` frame 中的几何落点 |

- `candidates`
- `confidence`
