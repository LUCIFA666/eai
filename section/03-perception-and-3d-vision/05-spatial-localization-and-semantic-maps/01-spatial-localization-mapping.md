# 空间定位与建图

> 难度：[中级] | 预计用时：55 分钟
> 先修：[力控证据链](../04-interactive-perception/07-force-control-evidence.md) → [三维重建与场景表征](../01-geometric-perception-foundations/05-3d-reconstruction.md)
> 建议：把本页理解成“机器人如何持续知道自己在哪里”的那一层，而不是把它和对象检测混成一类感知任务。

目标：理解 VO、VIO、SLAM、重定位和语义地图各自解决什么问题，并知道它们与本体状态估计、对象感知和统一感知接口之间怎样分工。

> 分工：本页讲定位与建图在**感知系统中的角色**（视觉建图与空间记忆）；机器人状态字段、底盘状态和定位坐标约定见 [机器人状态观测](../../02-robotics-foundations/04-robot-state-observation.md) 与 [定位坐标约定](../../02-robotics-foundations/03-spatial-relations-and-frame-conventions/04-localization-frame-conventions.md)。

## 先建立直觉

前面很多页面都在回答“外部世界里有什么”。这一页转向另一个同样关键的问题：

**机器人自己现在在环境中的哪里？**

如果这个问题答不清，前面的很多感知结果都会失去上下文：

- 之前建好的地图没法继续复用。
- 桌面、墙面和障碍物的位置会在不同回合之间漂移。
- 同一个物体的历史观测难以在长时间任务中对齐。
- 回放和失败分析时，很难判断问题是对象检测错了，还是机器人自己定位飘了。

所以空间定位与建图关心的不是单个对象，而是**机器人与整个场景的时空关系**。

## 本页目标

这一页读完后，我们希望能一起把下面几件事说明白：

- 区分 VO、VIO、SLAM、重定位、语义地图分别在系统里承担什么角色。
- 解释为什么“本体状态估计”和“空间定位”相关但不相同。
- 写出一份最小 `localization_state`，说明地图坐标系、位姿来源、跟踪状态和失败码。
- 判断一份定位结果什么时候还能继续用，什么时候应该触发重定位、降级或停机。

## 先把几个术语分清

| 术语 | 它在解决什么 |
|---|---|
| VO | 只用视觉估计相邻时刻运动 |
| VIO | 用视觉加 IMU 估计更稳定的短时运动 |
| SLAM | 一边定位，一边构建和维护地图 |
| Relocalization | 跟丢之后重新找回自己在地图中的位置 |
| Semantic Map | 在几何地图上继续叠加语义标签 |

可以把它们理解成从“短时相对运动”到“长期可复用空间记忆”的一条谱系。

## 它和机器人本体状态估计有什么区别

初学者很容易把“空间定位”与“机器人本体状态估计”混成一件事。更准确地说：

- 本体状态估计关心的是关节、底盘、末端、IMU 等内部状态。
- 空间定位与建图关心的是机器人相对环境的全局或局部位姿。

这两者会互相帮助，但职责不同：

- 编码器、轮速计、IMU 能帮助定位更稳定。
- 地图、回环和重定位又能反过来约束长时间漂移。

所以如果把本体状态估计理解成“我自己现在怎样”，那空间定位更像“我自己现在在环境里的哪里”。

## 从传感器到可用地图位姿的典型链路

```text
image / imu / wheel / joint odom
  -> relative motion estimate
  -> local trajectory
  -> map update
  -> loop closure or relocalization
  -> globally consistent robot pose
```

如果把前面的重建页看作“地图表示”，那这一页更强调“地图如何在任务中持续被维护和使用”。

## VO、VIO、SLAM 最容易混在哪

这三个词常常被一起提，但它们不完全是一回事：

| 名称 | 更偏回答什么问题 |
|---|---|
| VO | “这一小段时间我相对上一帧怎么动了？” |
| VIO | “如果把 IMU 也用上，这段短时运动能不能更稳？” |
| SLAM | “我一边走，一边能不能维护一份长期可复用地图，并把全局漂移压住？” |

所以可以把它们粗略理解成：

- VO/VIO 更偏局部运动估计。
- SLAM 更偏长期一致的定位与地图维护。

## 为什么重定位不是“附加功能”，而是主流程的一部分

机器人长期运行时，定位不可能永远完美。遮挡、快速转身、纹理稀缺、反光、动态人群都会导致跟踪丢失。  
这时系统需要的不只是“继续算”，而是要能明确进入一种恢复模式。

所以比“定位永不失败”更现实的工程目标是：

- 失败能被及时发现。
- 失败后有清晰的恢复路径。
- 恢复失败时能触发保守动作，而不是继续盲走。

这就是为什么 `tracking_state`、`confidence`、`failure_code` 在定位页里比在很多纯视觉任务里更重要。

## 移动操作里最常见的三类地图

| 地图类型 | 更适合做什么 |
|---|---|
| Occupancy Map | 导航、避障、安全边界 |
| Metric 3D Map | 机械臂操作、几何查询、桌面和障碍物定位 |
| Semantic Map | 找物体、找区域、任务级语义检索 |

移动操作常常会把这三层叠在一起用：

- 底盘靠占据地图规划大致路径。
- 机械臂靠局部 3D 地图做精细操作。
- 任务系统靠语义地图理解“厨房台面”“储物架”“充电座”。

## 语义地图为什么不是“给地图加几个标签”这么简单

语义地图的难点不在于把词贴上去，而在于让语义和几何长期保持一致。  
比如“左边台面”这个标签，只有在下面几件事都成立时才有意义：

- 地图没有全局漂移到别处。
- 标签对应的区域仍然是当前场景里的那个台面。
- 新观测能和历史语义对齐，而不是越积越乱。

所以语义地图往往依赖：

- 稳定的几何地图。
- 稳定的定位链。
- 清楚的地图版本与更新时间。

## 一个最小定位与地图记录

```yaml
localization_state:
  timestamp: 2026-06-02T10:42:00.000Z
  frame_id: map
  robot_base_frame: base_link
  robot_pose:
    xyz_m: [1.42, -0.33, 0.0]
    quat_xyzw: [0.0, 0.0, 0.12, 0.99]
  pose_source: vio_slam
  map_id: lab_floor_01
  tracking_state: healthy
  confidence: 0.88
  failure_code: null
```

这类结果和对象位姿一样，也必须说清：

- 参考坐标系。
- 时间戳。
- 当前位姿来自哪种估计链路。
- 当前跟踪状态是否可靠。
- 现在用的是哪一份地图。

## 一份定位结果什么时候不能继续交给下游

下面这些情况，即使系统还能吐出一个 pose 数值，也不建议继续当成“正常定位”使用：

| 情况 | 为什么危险 |
|---|---|
| 连续几帧 pose 明显跳变 | 说明跟踪已不稳定 |
| 地图坐标和局部观测越来越对不上 | 可能已经发生累计漂移 |
| `tracking_state` 已经 degraded 或 lost | 下游如果继续相信它，会把错误放大 |
| 旧地图明显不再匹配当前环境 | 家具、障碍变化会直接误导规划 |
| 只输出位姿，不说明 map_id 和 pose_source | 无法复盘问题来自哪里 |

所以“有一个姿态数值”并不等于“已经有一份可用定位结果”。

## 常见失败模式

| 失败 | 现象 | 常见原因 |
|---|---|---|
| 轨迹漂移 | 越走越偏，地图和现实对不上 | 纯 VO 长期累积误差 |
| 跟踪丢失 | 位姿突然跳变或直接失效 | 纹理不足、快速运动、遮挡 |
| 回环错误 | 地图被错误闭环拉扯 | 相似场景误匹配 |
| 语义和几何错位 | 物体标签落在错误位置 | 时间戳或 frame 不一致 |
| 地图过时 | 家具位置已变，系统仍信旧图 | 缺少在线更新或地图版本管理 |
| 局部稳定、全局错误 | 短时运动看着平滑，但全局早已漂走 | 缺少全局约束或重定位失败 |

## 为什么这一页要放在感知接口之前

这是因为感知接口页最终要汇总的不只是对象和接触，还包括：

- 机器人当前在哪个地图坐标系里。
- 这份对象观测是相对于哪个地图或哪个基座表达的。
- 当前定位状态是否健康。

如果这一层没讲清，后面的统一 observation 很容易只剩“对象结果的打包”，而缺少真正可闭环的空间上下文。

## 练习

### [观察] 画出定位与建图的分工图

把下面这些模块串起来，并说明谁产出什么：

- IMU / image
- VO 或 VIO
- map update
- relocalization
- planner

读到这里时，我们最好已经能说清“地图表示”和“在线定位”分别由谁负责。

### [复现] 写一份最小 localization state

至少包含：

- `frame_id`
- `robot_pose`
- `pose_source`
- `map_id`
- `tracking_state`
- `confidence`
- `failure_code`

完成后，可以先用下面几条检查这一部分是否已经到位：
- 能说明为什么“有 pose”还不够，还必须写清它是不是当前可信的 pose。
- 能说明定位失败时，下游更适合重定位、降级还是停机。
