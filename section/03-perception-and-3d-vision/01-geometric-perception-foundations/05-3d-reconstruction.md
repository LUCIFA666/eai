# 三维重建与场景表征

> 难度：[中级] | 预计用时：55 分钟
> 先修：[点云配准](04-pointcloud-registration.md)
> 建议：把本页理解成“从单帧点云走向可复用场景记忆”的桥梁，再进入后面的对象级检测与分割。

目标：理解为什么机器人不能只停留在“单帧点云”，并学会区分 TSDF、占据栅格、NeRF、3D Gaussian Splatting 这些场景表示各自适合什么、不适合什么。

## 先建立直觉

到目前为止，我们已经能从图像和深度恢复一帧点云，也知道怎样把多帧点云配到同一坐标系里。  
但如果系统仍然只保存“这一帧看到了什么”，很多任务还是做不稳：

- 相机一转过去，刚才看见的桌面和障碍物就“忘了”。
- 目标暂时被遮挡后，系统很难利用历史观测补洞。
- 规划器每次都只能基于一帧 noisy 点云做决策。
- 回放、分析和长期任务缺少一份统一的场景记忆。

所以三维重建的真正意义，不是把场景做成一个更好看的 3D 模型，而是把多帧观测融合成**机器人可复用的空间记忆**。

## 本页目标

这一页读完后，我们希望能一起把下面几件事说明白：

- 区分“单帧点云”“多帧融合地图”“高保真渲染场景表示”分别在解决什么问题。
- 解释 TSDF、占据栅格、NeRF、3D Gaussian Splatting 在具身任务中的工程位置。
- 写出一份最小 `scene_representation`，说明坐标系、位姿来源、更新时刻和可信度。
- 判断一份重建结果什么时候可以交给避障或抓取模块，什么时候必须拒收。

## 先把几个关键概念讲清楚

**scene reconstruction**：把来自多个时刻、多个视角的观测融合成统一场景表示。这里的重点不是“多”，而是“统一到同一坐标系并持续可查询”。

**scene representation**：场景在系统内部的保存方式。它可能是点云、体素、TSDF、占据地图，也可能是 NeRF 或 3D Gaussian Splatting 这类连续或可渲染表示。

**fusion**：把新观测并入已有场景表示的过程。融合不是简单叠加，而是要处理噪声、遮挡、重复观测和历史信息。

**unknown space**：机器人还没看见的区域。对导航和安全来说，未知区域和“空区域”绝对不是一回事。

## 从单帧观测到场景表示的基本链路

```text
RGB / depth / pose
  -> 单帧点云或深度体素
  -> 配准到统一坐标系
  -> 多帧融合
  -> 构建可查询的场景表示
  -> 提供给抓取、避障、回放或评测
```

这条链路里最容易被低估的两个前提是：

- 帧间位姿必须足够准，否则融合会“糊掉”。
- 时间戳和坐标系必须一致，否则会出现幽灵表面、重影和错误障碍物。

## 为什么“多帧融合”不等于“把点全堆起来”

新手很容易把重建理解成“把每一帧点云叠在一起”。这当然能得到一个更密的点集，但通常还不够：

- 它不会显式区分空、占据和未知。
- 点云噪声会在历史累积后变成毛刺和厚边。
- 下游要做碰撞查询、表面法向估计或自由空间判断时，不够方便。

所以真正工程化的场景表示，通常会比“累计点云”多一层结构化编码。

## 常见表示各自适合做什么

| 表示 | 它保存什么 | 最擅长做什么 | 最常见短板 |
|---|---|---|---|
| Multi-frame Point Cloud | 多帧叠加后的点集 | 可视化、局部几何检查 | 噪声累积，不善表达未知空间 |
| TSDF | 截断符号距离场 | 平滑表面重建、法向估计、碰撞查询 | 需要体素内存，范围大时成本高 |
| Occupancy Grid / Voxel Map | 空、占据、未知 | 导航、避障、安全边界 | 表面细节不如 TSDF |
| Mesh | 显式三角面片 | 可视化、接触面分析 | 更新复杂、动态场景处理麻烦 |
| NeRF | 连续辐射场 | 新视角渲染、细节外观建模 | 直接执行不方便，训练和查询成本高 |
| 3D Gaussian Splatting | 可渲染高斯场景 | 快速渲染、回放、视觉记忆 | 几何可执行接口仍需额外设计 |

对零基础读者来说，这张表最想让你先记住一件事：

**场景表示不是“谁更先进”就用谁，而是先看它要服务几何执行，还是服务高保真外观。**

## 为什么机器人里常优先学 TSDF 和占据地图

在具身任务中，TSDF 和占据栅格通常比 NeRF 更值得优先掌握，因为它们和动作系统贴得更近。

TSDF 更擅长回答：

- 物体和桌面的表面在哪里。
- 局部法向大概朝哪边。
- 哪些细小孔洞可以靠多帧融合补起来。

占据地图更擅长回答：

- 这里能不能走。
- 这里是不是障碍。
- 这块区域是空、占据还是未知。

如果你把这两者记成一句话：

- TSDF 更偏“表面和几何”。
- Occupancy 更偏“空间和安全”。

通常就不容易混。

## NeRF 和 3D Gaussian Splatting 在本章里的位置

这两类方法近年很热门，但在具身系统里要特别注意它们和传统几何地图的职责边界：

| 方法 | 优势 | 对机器人真正有帮助的地方 | 直接上手的限制 |
|---|---|---|---|
| NeRF | 连续视角、外观细节强 | 视觉记忆、离线场景重建、感知增强 | 训练慢，几何和动作接口不天然直接 |
| 3D Gaussian Splatting | 渲染快、回放体验好 | 高保真回放、场景可视化、合成数据支持 | 可执行碰撞模型仍需额外抽取 |

所以它们更像“高保真场景记忆”，而不是天然可直接交给抓取规划器的碰撞地图。

## 把这几类表示放回机器人任务里看

| 任务 | 更常优先依赖什么表示 |
|---|---|
| 机械臂抓取前检查桌面与障碍物 | TSDF / 局部 3D 几何地图 |
| 移动底盘规划大致路线 | Occupancy Map |
| 长时间场景回放与复盘 | 3D Gaussian Splatting / Mesh / 多帧点云 |
| 离线高保真视觉记忆或新视角合成 | NeRF |

这也是为什么“重建效果好看”并不等于“动作一定更稳”。  
动作系统要的是可查询、可更新、可验证的结构，而不仅是漂亮外观。

## 一个最小场景表示 contract

```yaml
scene_representation:
  scene_id: lab_table_01
  frame_id: world
  timestamp: 2026-06-02T10:30:00.000Z
  representation_type: tsdf
  source_frames: 64
  voxel_size_m: 0.01
  bounds_xyz_min_m: [-1.0, -1.0, 0.0]
  bounds_xyz_max_m: [1.0, 1.0, 1.5]
  pose_source: vio
  update_mode: incremental
  confidence: 0.81
  failure_code: null
```

这个结构里最容易被忽视、但特别重要的字段是：

- `frame_id`：不然下游不知道这份地图到底在哪个坐标系里。
- `pose_source`：不然无法追溯地图漂移究竟是融合问题还是定位问题。
- `update_mode`：不然别人不知道这是一帧性的离线重建，还是持续更新的在线地图。

## 一份重建结果什么时候可以交给下游

下面这几种场景，通常可以考虑把结果交给避障、抓取或回放模块：

- 视角覆盖已经足够，关键工作区不再存在大块未知区域。
- 融合后的桌面、障碍和目标表面位置稳定，不随新帧明显跳动。
- 使用的 `frame_id` 和位姿来源与整个系统一致。
- 对下游真正关心的局部区域，几何精度已经够用。

但下面这些情况，即使“有一份重建输出”，也建议拒收：

| 情况 | 为什么危险 |
|---|---|
| 关键区域仍大量未知 | 抓取或避障规划会过度乐观 |
| 新帧一并入就明显重影 | 融合位姿链有问题 |
| 地图坐标系和对象坐标系不一致 | 下游会把几何当成别的地方 |
| 只适合渲染的表示被直接当碰撞地图 | 外观看起来对，执行却不可靠 |

## 常见失败模式

| 失败 | 现象 | 常见原因 |
|---|---|---|
| 融合重影 | 同一物体边缘出现多层表面 | 位姿漂移、时序不对齐 |
| 表面被抹平 | 细节消失、边缘发糊 | 体素太粗、滤波过强 |
| 空洞长期存在 | 某些区域一直缺数据 | 遮挡严重、视角覆盖不足 |
| 地图坐标漂移 | 老地图和新观测逐渐对不上 | 全局定位不稳 |
| 把未知当空 | 看起来畅通，其实只是没看见 | 地图语义设计不清 |
| 外观很好但不可执行 | 渲染很漂亮，碰撞查询却不好用 | 表示偏外观，不含足够几何约束 |

## 为什么这一页放在检测与分割之前

这一页讲的是**场景级记忆**，而不是对象级识别。  
它和后面的对象检测不是谁替代谁，而是回答不同粒度的问题：

- 重建更关心“整张桌面、整片环境怎样长期表达”。
- 检测与分割更关心“这一帧里哪个区域是任务相关对象”。

换句话说，重建在回答“世界整体长什么样”，检测在回答“这次操作要关注哪一块”。

至少包含：

- `scene_id`
- `frame_id`
- `representation_type`
- `source_frames`
- `pose_source`
- `confidence`
- `failure_code`

- 能说明为什么只保存一个 `.ply` 文件通常还不够。
